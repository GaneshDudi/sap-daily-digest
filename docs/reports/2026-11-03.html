Debugging a custom function module that an F110 run never calls

The two F110 threads show a common failure: the team traces the symptom but cannot find the call site. An empty ST22 only means no dump. A missing ST12 entry only proves absence if the trace filter matches the right user, job and program. The posts also do not say whether the FM is called from a user exit, BAdI, BTE or the payment medium.

Start from the outcome. Check SOST and SCOT to see whether any mail request was created. If none exists, work backwards. Run a where-used list on the FM and on the calling program. Open the F110 job in SM37 and read the job log to see which program actually runs. Then look at the payment medium and output configuration, since standard remittance advice is driven from there.

To debug the background step, set a breakpoint in the FM and use a background debugging method such as JDBG on the job. External breakpoints in ADT also work if the job user matches your debug user setting. The post does not confirm which exit is used, so the where-used list is the first step.

  • Where-used on custom FM
  • SOST/SCOT send log
  • Background debugging with JDBG
  • ST12 filter by job and user
  • F110 exits, BAdIs and BTEs

Unmanaged RAP: what you own

In an unmanaged RAP business object the behavior definition is declared with unmanaged implementation in class .... The framework does not persist anything for you. You implement create, update, delete, read and lock in the handler class, and the save phase in the saver class.

The key pattern is the transactional buffer. Handler methods in the interaction phase change a buffer, usually static class attributes, and do not touch the database. In the save sequence, finalize, check_before_save and save write the buffer to the database. The cleanup method clears the buffer afterwards. Writing to the database in a handler method breaks the RAP transaction model.

The part 3 post covers this, but the excerpt shows no code. When teaching, have students implement the buffer and saver methods themselves and see what breaks when they write directly in the handler.

  • unmanaged implementation
  • Handler vs saver class
  • Transactional buffer
  • finalize / check_before_save / save / cleanup
  • Interaction phase vs save phase

Senior A custom function module that should send remittance emails after an F110 run is never executed, and ST22 is empty. How do you investigate?

I start from the outcome and check SOST and SCOT to see whether any mail request was created. If not, I check the F110 job in SM37 to see which program and step ran. A where-used list on the function module shows the call site, which could be a user exit, BAdI, BTE or payment medium output. I also check the output configuration that drives standard remittance advice. To debug a background job, I set a breakpoint in the FM and use JDBG or a matching external breakpoint for the job user. An empty ST22 only means no dump, and an ST12 trace with a wrong user, job or program filter proves nothing.

Senior In unmanaged RAP, where should database changes happen and why?

In unmanaged RAP, handler methods for create, update and delete work during the interaction phase. They should only change the transactional buffer, such as static class attributes. Database writes belong in the save phase, in the saver class methods, after finalize and check_before_save have run. cleanup then clears the buffer. This keeps the RAP transaction model consistent: if validation fails, nothing was persisted. Writing directly in a handler would persist data that the framework might still roll back, so it breaks the model.

Architect A requirement needs a field that exists only in unreleased CDS views on S/4HANA Cloud Public Edition. What are your options?

Custom CDS views and ABAP Cloud code in Public Edition may use only released objects, so building on the unreleased view is not allowed. I would first check the release status in the View Browser.
