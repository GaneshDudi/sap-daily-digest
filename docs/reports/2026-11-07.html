Deep dives

Diagnosing a BAPI that fails on part of a mass update

The question in ref 22 offers four call modes, but they solve different problems. A plain CALL FUNCTION runs in the same work process and LUW. STARTING NEW TASK starts an asynchronous call in a separate session, so it has its own LUW and the caller does not see the result directly. IN UPDATE TASK registers an update function module that runs at COMMIT WORK. IN BACKGROUND TASK registers a tRFC call that runs after COMMIT WORK. None of them is a fix for a failure that has not been diagnosed.

Start with the RETURN table. After each BAPI call, read all messages of type E and A, and check sy-subrc for exceptions. Typical causes of a roughly 50% failure rate are lock conflicts, because the standard transaction already holds an enqueue on the same object, or the BAPI being called in a loop with state left over from the previous call. The post gives no evidence for any of these, so they are hypotheses to test, not conclusions.

The commit is the risky part. BAPI_TRANSACTION_COMMIT inside an enhancement of a standard transaction ends the transaction's LUW early. Data already prepared by the standard program may be committed or lost, and later rollback logic no longer works. If the update must be independent of the standard transaction, a separate task or a bgRFC/tRFC unit is a deliberate design choice. It then needs its own error handling and logging. If it must be part of the same LUW, no commit should be issued and the BAPI should run in the existing LUW.

A minimal pattern: call the BAPI, evaluate RETURN with a helper, collect failures in an application log (SLG1), and only then decide on the commit location. Use BAPI_TRANSACTION_ROLLBACK for failed units only if you own the LUW.

  • LUW and COMMIT WORK
  • STARTING NEW TASK vs IN UPDATE TASK vs IN BACKGROUND TASK
  • BAPI RETURN table evaluation
  • Enqueue/lock conflicts
  • Commits inside enhancements of standard transactions

Clean-core options when classic BAdIs are not available (MM02 on Public Edition)

Ref 24 asks for a BAdI in the classic GUI transaction MM02 on S/4HANA Cloud Public Edition, similar to CMD_PRODUCT_VALIDATE for the Fiori app Manage Product Master Data. The post has no answer and does not say whether MM02 is available in that edition. The core issue is that Public Edition limits extensibility to released extension points.

The working method is to confirm first which UI the business user uses, then look in the released BAdI and extension catalogue for that edition. Do not assume that a hook available for the Fiori app also fires in a classic transaction. The post itself describes CMD_PRODUCT_VALIDATE only as the Fiori-side hook.

For teaching, compare three questions: Is the object (product master) behind a released API or BAdI? Does the validation belong in the data layer (a released validation hook) or the UI? Can the business process be moved to the Fiori app where a released hook exists? Answering these before writing code avoids building on an unreleased extension point.

Finding the real failing layer: 429 in API Management and 500 in Work Zone

Refs 33 and 26 are different symptoms with the same debugging principle: identify which component produced the error before changing configuration. In ref 33, the team has no quota or spike-arrest policy yet sees HTTP 429. The post does not show whether API Management or the SAP backend returned it. Response headers, the API Management trace and analytics show where the status code originates. Whether SAP applies a default limit is a claim to check in the official documentation.

In ref 26, apps open in FLP but some return 500 in Work Zone. The content provider reads /sap/bc/ui2/cdm3/entities. Fetch that endpoint for a working and a failing app and diff the JSON for missing properties, component names, semantic objects or URLs. Then check ST22, SLG1 and the gateway log for the exception behind the 500, because the post only cites the browser console.

The common step is to compare a working and a failing case and collect server-side evidence, not to try SAP notes one after another.

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A standard BAPI called in a loop from a customer enhancement updates only about half the records. How do you diagnose it before changing the code?

I would first check what the BAPI reports. After every call I read the RETURN table for E and A messages and check sy-subrc for exceptions, and I log them per record, for example in SLG1. Then I look for lock conflicts, because the standard transaction may hold an enqueue on the same object. I also check whether state from a previous iteration affects the next call. Only after that would I decide where a commit belongs. Adding BAPI_TRANSACTION_COMMIT inside an enhancement can end the standard transaction's LUW early and make its rollback logic unreliable.

Question: BAPI not updating during mass update
Mid-level Explain the difference between CALL FUNCTION STARTING NEW TASK, IN UPDATE TASK and IN BACKGROUND TASK.

STARTING NEW TASK starts an asynchronous call in a separate session with its own LUW. The caller continues without waiting, and results can be received through a callback if one is registered. IN UPDATE TASK registers an update function module. The system runs it in an update work process when COMMIT WORK is executed, and it is discarded on ROLLBACK WORK. IN BACKGROUND TASK registers a tRFC call, which is executed after COMMIT WORK and can be repeated if it fails. So they differ in timing, transactional coupling and error handling. They are not interchangeable fixes for a failing update.

Architect Some ABAP-hosted UI5 apps return HTTP 500 in Work Zone through a CDM3 content provider but work in FLP. How do you approach it?

I would treat it as app-specific, since only some apps fail. I call /sap/bc/ui2/cdm3/entities for a working and a failing app and compare the JSON, looking for missing properties, component names, semantic objects or URLs. In parallel I look for the server-side exception behind the 500 in ST22, SLG1 and the gateway log, because the browser console alone gives too little. I would then check the SAP notes that match the symptom, such as those referencing the CDM3 handler. The goal is to find the real cause before applying notes at random.
