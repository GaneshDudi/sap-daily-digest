Custom CI_COBL field: tracing the four gates

Ref 56 says a field in the CI_COBL append can be active in BSEG and ACDOCA and still not show on ME51N, ME21N or FB60. The DDIC and table layer is only the first step. The screen layer is controlled separately.

The post names four gates. First, OXK3 control entries, which must exist in every client. Second, OBC4 with OB41 field status. Third, OME9. Fourth, a custom subscreen in SAPLKACB that hosts the field. The post adds a troubleshooting table and a go-live checklist, which are not shown in the excerpt.

The practical method is to test the gates in order and record the result of each, rather than changing several things at once. Do not take the sequence on trust: check each setting in your own system and release. The client dependency of OXK3 is a typical reason a field works in development and not after transport to another client.

  • CI_COBL append
  • OXK3 per-client entries
  • OBC4/OB41 field status
  • SAPLKACB subscreen
  • Silent UI failure

RAP message targets on composition associations

Ref 70 describes a Fiori Elements V4 app on SAPUI5 1.120 (tested up to 1.151). The parent _Items has composition _PackItems, and a @UI.lineItem on _PackItems.PackType generates an sap.ui.mdc.MultiValueField. Messages on scalar properties highlight the field. A message for 'at least one _PackItems entry' targets $Parameter/_it/_Items(...)/_PackItems and does not.

In RAP, a validation returns messages through reported, and the target is set with %element fields or %path. The poster asks which of these to use and whether the message belongs on the parent association or the child field PackType. The source gives no answer.

A reasonable test plan is to emit the same message three ways: on the parent association, on the child PackType element, and with %path into the child. Then inspect the OData V4 message target in the browser network tab and see which control picks it up. Check the result against the SAP documentation for RAP messages and Fiori Elements, since the post confirms no fix.

  • reported with %element/%path
  • OData V4 message target
  • Composition association
  • MultiValueField
  • Minimum-cardinality validation

Lookup failure on an LIFNR field in a custom table

Ref 74 reports that a custom table is found by po_number but not by agent_vendor with value 9876543, for every record. The data element is LIFNR, which is CHAR 10 and normally carries the ALPHA conversion exit.

A conversion exit applies on screen input and output. The database stores the internal form, for example 0009876543. A search that compares the external form against the stored one finds nothing. The check is to look at the raw stored value in SE16 or through a SELECT, and then at how the search passes the value (selection screen, search help or program). The post does not say how the search is implemented.

The fix, if this is the cause, is to apply CONVERSION_EXIT_ALPHA_INPUT or use a typed field with the exit so the WHERE clause receives the internal form. This is a hypothesis from the described symptoms, not a confirmed answer.

  • ALPHA conversion exit
  • Internal vs external format
  • LIFNR CHAR 10
  • Raw value check in SE16

Senior A custom field in a CI_COBL append is active in BSEG and ACDOCA but missing on ME21N and FB60. How do you approach it?

Activation in the tables only covers the data layer. The screens depend on separate configuration. According to the walkthrough, I would check four things in order: OXK3 control entries, which must exist in every client; the OBC4 and OB41 field status; OME9; and a custom SAPLKACB subscreen that hosts the field. I would record the result of each gate before changing the next, so I know which one fixed it. I would also compare clients, since missing OXK3 entries in the target client are a likely cause after a transport. I would confirm the sequence in my own system and release instead of trusting the post.

Blog: Adding a custom Coding Block field (CI_COBL) to ME51N, ME21N
Senior A RAP validation message targets a composition association and the generated MultiValueField is not highlighted. How would you investigate?

First I would confirm what the backend returns: the message target in the OData V4 response, for example the path to the association _PackItems. Scalar field messages work, so the issue is specific to a collection-valued association. I would send the same message in three ways: on the parent association, on the child field PackType, and with %path into the child. Then I would check in the network trace which target string the client receives and which control reacts. Only after that would I consider manual value state handling. The source does not confirm a fix, so I would check SAP's documentation for RAP messages and Fiori Elements behaviour and say so if it is a known limitation.

Mid-level A custom table is found by PO number but not by a vendor field typed LIFNR. What do you check?

I suspect a storage-format mismatch. LIFNR is CHAR 10 with the ALPHA conversion exit, so the database holds the padded internal form such as 0009876543. A search using the external value 9876543 will not match in a WHERE clause. I would look at the raw stored value in SE16 or a SELECT, and at how the search passes the value, whether through a selection screen, a search help or custom code. Conversion exits run on screen input and output, not inside Open SQL. If confirmed, I would apply CONVERSION_EXIT_ALPHA_INPUT or use a field typed with the exit. I would also check that the key field and types match between search and table. The report gives no confirmation, so this is a hypothesis to test.

Class idea

Silent failures in ABAP and RAP: debugging by layers

Today's questions share one pattern: data exists but the screen or query shows nothing. These are a CI_COBL field missing from screens (ref 56), a RAP message not highlighting a control (ref 70), an LIFNR lookup returning no rows (ref 74) and an eCATT type mismatch (ref 79).

  1. Layered thinking: data, conversion, configuration, UI
  2. CI_COBL: the four gates and their order
  3. ALPHA exit and internal vs external format in WHERE clauses
  4. RAP reported messages: %element, %path and OData message targets
  5. Reading the message target in the browser network trace
  6. eCATT parameters after a DDIC change
  7. Writing a debugging checklist per symptom

Hands-on exercise: Provide a custom table with an LIFNR field filled with padded values, and a small RAP BO with a composition child and a cardinality validation. Students (1) fix the lookup with the correct conversion, and (2) emit the validation message on three targets in ADT, then inspect the OData response in a Fiori Elements preview and report which target highlights the control.
