Deep dives

The most valuable technical posts, explained.

Testing global authorization in RAP with ABAP Unit

The BDEF declares authorization master ( global ). The behavior pool's GET_GLOBAL_AUTHORIZATIONS method receives requested_authorizations and fills result. For each requested flag (%create, %update, %delete equal to if_abap_behv=>mk-on), the handler runs AUTHORITY-CHECK OBJECT 'Z_RAUTH_D1' ID 'ACTVT' FIELD '01', '02' or '06'. It sets the result to if_abap_behv=>auth-allowed or auth-unauthorized based on sy-subrc.

The test class is local, FOR TESTING, with DURATION SHORT and RISK LEVEL HARMLESS. It declares a FRIENDS relation to the handler class so it can create the object and call the method. The article's weak point is the negative case. It asserts only assert_not_initial, which passes whether the result is allowed or unauthorized. A real test asserts %create = if_abap_behv=>auth-unauthorized.

The second problem is that AUTHORITY-CHECK reads the running user's authorizations, so the test result depends on the system and user. Options: run with a test user whose roles are known, or move the check into a small class behind an interface that a test double can replace. The article's text does not cover this.

The post mentions ABAP Coverage in ADT and the test doubles (CDS, OSQL, behavior test environment), but the shown code doesn't set up an environment.

  • authorization master ( global )
  • GET_GLOBAL_AUTHORIZATIONS
  • if_abap_behv=>auth-allowed / auth-unauthorized
  • FOR TESTING ... FRIENDS
  • Test seam for AUTHORITY-CHECK

BEHAVIOR_ILLEGAL_STATEMENT in EML calls: reading the dump

The dump arises in program SAPLCMFE when MESSAGE E runs while the BO implementation of R_WBSBILLOFMATERIALTP is active. RAP restricts statements that interrupt processing, such as classic error messages, during behavior implementation phases. The dump itself warns that the true error may be at a higher call level.

RAP convention is to return messages through the reported and failed structures. Our post doesn't show the EML code, so this guidance is general RAP practice, not a confirmed fix for this case.

Method: open the dump's call stack in ST22 or ADT, and find the first frame outside the SAP-internal code. Then check which input made the legacy code raise an error (a missing mandatory field, wrong entity key, or an invalid sequence). Write the MODIFY ENTITIES OF I_WBSBillOfMaterialTP call with FAILED and REPORTED captured, followed by COMMIT ENTITIES, and read the results before assuming a platform bug.

  • EML MODIFY ENTITIES / COMMIT ENTITIES
  • FAILED and REPORTED response structures
  • BEHAVIOR_ILLEGAL_STATEMENT
  • Reading ST22 call stack

ADT save error SEDI_ADT016: what to check

The save is a PUT to /sap/bc/adt/oo/classes/<class>/source/main with lockHandle and corrNr. The backend answers ExceptionResourceSaveFailure, T100 message SEDI_ADT 016: 'SAP code was changed outside of modification brackets'. The report is from ADT 3.62.0 against 7.58 SP1, and no cause was confirmed.

The message implies the server treats the class as SAP-delivered code with modification handling. Checks: is the object really a Z class or does it contain SAP code, is the modification assistant active for it, does SE95 show existing modifications, and has an earlier change introduced an empty PROTECTED SECTION? Compare the current source with the original version.

Use the ADT communication log to see the actual request and response. These are diagnostic steps to try, not a confirmed fix.

  • Modification assistant
  • SE95 modifications
  • ADT communication log

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior You unit-test a RAP GET_GLOBAL_AUTHORIZATIONS method that uses AUTHORITY-CHECK. What makes the test unreliable and how do you fix it?

AUTHORITY-CHECK reads the authorizations of the user running the test, so the outcome depends on roles in that system. A test that passes in a developer system may fail in QA. Weak assertions make it worse, for example assert_not_initial on the result does not distinguish auth-allowed from auth-unauthorized. Assert the exact value, such as %create = if_abap_behv=>auth-unauthorized. To control the outcome, either run with a test user whose roles are known, or move the check behind an interface that a test double can replace. Then test each activity (01, 02, 06) in both allowed and refused states.

Blog: Testing AUTHORITY-CHECK in SAP RAP with ABAP Unit
Senior An EML call to a released BO ends in BEHAVIOR_ILLEGAL_STATEMENT with MESSAGE E in a standard program. How do you approach it?

The dump says a MESSAGE E ran while a BO implementation was active, which RAP does not allow. The dump also warns the real error may be at a higher call level. I open the call stack and find the first frame outside the SAP internals, then check what input made the legacy code raise an error: missing mandatory fields, wrong keys or an invalid sequence. I make the EML call with FAILED and REPORTED captured and check them before COMMIT ENTITIES. I would not treat the dump line as the cause. If the input is valid and the dump persists, it goes to SAP as a product issue with the stack.
