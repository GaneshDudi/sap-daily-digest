Diagnosing CDS performance with the ADT Dependency Analyzer

The post (ref 4) starts a CDS performance tuning series. Before you read execution plans, you first find out which part of the stack is responsible. The ADT Dependency Analyzer offers three views for this: the SQL Dependency Tree, the SQL Dependency Graph and the Complexity Metrics. The example is a Sales Order Analytics stack.

The tree shows which views and tables a CDS entity ends up reading through its layers. The graph shows the same relationships as a network, so you can spot shared or repeated dependencies. The complexity metrics condense the stack into numbers, which let you compare before and after a refactoring. The post also covers inspecting the generated SQL, because code pushdown only helps if the SQL that reaches HANA is reasonable.

Workflow: analyse the top consumption view and find the layer that adds the most joins or tables. Then check whether those joins are needed for the consumer's actual field list. Fix the largest contributor first and re-measure. Do this before looking at the plan, so you know where to look in it.

The summary of the post does not give concrete thresholds, so treat the metrics as relative indicators and not as pass/fail limits.

  • Code pushdown

Enforcing policy in a BAdI with a SQL CTE: purchase requisition interlock

Ref 73 extends the BAdI ME_PROCESS_REQ_CUST so that manually created purchase requisitions cannot bypass safety stock rules. The thresholds are kept in a custom configuration table. The check uses a SQL Common Table Expression (CTE) to compare the requested quantity against consumption limits.

The design has two parts. Policy lives in data, in a config table, so changing a limit does not require a transport of code. The check lives in the BAdI at PR processing time, so it applies to every entry path, including manual ones. The CTE lets you build the intermediate aggregates and the comparison in one open SQL statement, executed on the database.

Things to watch in a real implementation (these are general ABAP practice, not stated in the source summary): keep the BAdI fast because it runs per item during the user's save, return a clear message through the BAdI's check mechanism, and make sure the SQL does not run once per item without need. Buffer the config table where possible.

The source summary has few details on the exact code, so check the original post for the statement itself.

Duplicate Event Mesh consumption in BTP ABAP: what to check

Ref 37 describes an ABAP environment with Event Mesh where one topic fans out to two queues (Q1, Q2). Two Event Consumption Model classes (ECM_Q1, ECM_Q2) exist. On each event, each ECM class runs twice, so four invocations appear instead of two. The author suspects the /IWXBE framework resolves all consumers of the topic for each queue message, without regard to which queue delivered it.

This is a hypothesis from the question, not a confirmed explanation. The configuration involved is an AMQP channel with an EEE Channel Binding and outbound and inbound topic bindings. If both queues are bound to the same inbound topic binding, every message from either queue would plausibly trigger both consumers.

Practical checks: look at how many inbound topic bindings point at the same topic, whether each queue has its own channel binding, and whether the two ECM classes are registered against the same topic. Also make consumers idempotent, since at-least-once delivery is the normal contract for message brokers. A fan-out to two queues in the same ABAP system is often better served by one queue and two consumers, or by a single consumer that dispatches.

  • /IWXBE
  • EEE Channel Binding
  • Idempotent consumers

Senior A CDS-based analytical query on a three-layer view stack is slow. How do you find which layer is responsible?

Start with the ADT Dependency Analyzer on the consumption view. The SQL Dependency Tree shows what each layer reads. The Graph shows shared or repeated dependencies. The Complexity Metrics give a comparable number for before and after. Then read the generated SQL to see what actually reaches HANA. Find the layer that adds the most joins or tables and check whether the consumer's field list needs them. Fix that layer first, for example by removing unused associations or flattening it, and re-measure. Only then move on to execution plans, so you know where to look.

Senior How would you stop users from bypassing a safety stock policy by creating purchase requisitions manually, and where would you keep the thresholds?

Implement the check in the BAdI ME_PROCESS_REQ_CUST, because it runs on every PR regardless of entry path. Keep the thresholds in a custom configuration table so the policy can change without a code transport. Use a SQL CTE to aggregate the consumption data and compare it with the limit in a single database-side statement. Keep the logic fast, since it runs during the user's save, and avoid running a query per item when one set-based statement will do. Return a clear message to the user when the check fails. This approach does not modify standard code.

Architect Two Event Mesh queues are bound to one topic and each of two ECM classes is invoked twice per event. How do you investigate, and how do you protect the system meanwhile?

First verify the configuration: how many inbound topic bindings exist for the topic, whether each queue has its own channel binding, and which ECM class is registered for which binding. The reporter suspects that /IWXBE resolves all consumers of the topic for every queue message, which would give 2 x 2 = 4 calls. That is unconfirmed, so test by removing one queue and counting calls. Check the IB Events monitor for the source queue of each call. As protection, make consumers idempotent, for example with a message ID check, since duplicates are possible with brokers anyway. If the design allows, use one queue and one dispatching consumer instead of fan-out to two queues in the same system.

Reading and tuning a layered CDS stack with ADT's Dependency Analyzer

A new CDS performance series (ref 4) starts with dependency analysis in ADT. Multi-layer CDS stacks are a common source of slow queries.

  1. Why layered VDM stacks hurt performance: join and association fan-out
  2. Open the Dependency Analyzer: SQL Dependency Tree vs Graph
  3. Read the Complexity Metrics and find the heaviest layer
  4. Inspect the generated SQL for the top view
  5. Decide what to fix: remove unused associations, push filters down, flatten a layer
  6. Re-measure after the change and compare the metrics
  7. Preview of the next step: execution plans

Hands-on exercise: Pick a multi-layer analytical CDS view in your system (for example, a sales-order-based one). Run the Dependency Analyzer on it. Record the tree depth and the complexity metrics. Identify the layer that contributes the most tables. Refactor one layer, re-run the analysis and compare the numbers.
