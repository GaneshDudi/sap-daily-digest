Deep dives

The most valuable technical posts, explained.

VALUE with BASE: structures versus internal tables

In DATA(itab2) = VALUE ty_itab( BASE itab ( comp99 = 3 ) ), the inner parentheses define a new table line. BASE copies all lines of itab, then one extra line is appended with comp99 = 3 and everything else initial. Existing rows are not changed. This is a row-append, not a column update.

For structures the semantics differ: VALUE ty_line( BASE structure comp99 = 3 ) starts from the structure's content and overrides the named component. Without parentheses on a table, VALUE ty_itab( BASE itab comp99 = 3 ) is a syntax error, since a table needs line specifications.

To set a component on every row there are two patterns from the thread. First, a FOR loop: VALUE ty_itab( FOR <line> IN itab ( VALUE #( BASE <line> comp99 = 3 ) ) ). Here BASE applies to a structure, so it overrides the field per row. Second, copy the table and modify it in place: MODIFY itab2 FROM VALUE #( comp99 = 3 ) TRANSPORTING comp99 WHERE comp99 <> 3.

The in-place MODIFY avoids building a second table in the constructor and states the intent directly. In reviews, ask whether BASE is applied to a table or to a line, and whether the parentheses mean 'new row'.

Architect Mass approval of 20 work items runs through an OData $batch changeset that calls a function module which commits workflow decisions. Where does the LUW boundary sit, and how would you handle item 14 failing?

A changeset gives all-or-nothing semantics at the request level only if everything in it can be rolled back. A function module that commits internally ends the database LUW, so earlier decisions are already persisted when item 14 fails, and the changeset rollback cannot undo them. I would first check whether the decision API commits or can be called in update-task or without commit. If it commits, I would not claim atomicity. Instead I would process items individually, return per-item success or failure in the batch response, and define compensation for the already-decided items, such as a reversal action. If atomicity is required, the decision logic must be wrapped so that a single commit happens at the end of the changeset. Fixes:
