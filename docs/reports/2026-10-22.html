Changing screen field properties in VA01/VA02 without editing LV09CF63

Ref 33 asks for a user exit or BAdI alternative to the form routine LV09CF63 for setting input/display properties of partner fields on the VA01/VA02 Partner tab, at header and item level. Editing a standard include or relying on a form-level modification is fragile: it is a modification, it needs adjustment at upgrade, and it is invisible to most enhancement searches.

Ref 111 is titled as a tip for exactly this case. Its one-line summary says you can lock the VA01 partner fields without changing LV09CF63 by reusing an existing SAP enhancement in the same function group. Only the headline is available to me, so I cannot confirm the details. Ref 100 supports the idea: it mentions the enhancement OIG_SAPLV09C_01, an IS-Oil implementation that runs on the current table control line in function group V09C. That is an existing hook where the current line is available.

A practical method: open function group V09C and screen 1000, then find the PBO modules that loop over the partner table control. Check for explicit enhancement points and enhancement implementations already active in the system. Look at what data the existing enhancement has in scope (the current table control line) and whether field attributes can be changed there. Verify all of this in your own release, as available hooks differ between systems and industry solutions.

Be careful about the trade-offs. Reusing an industry-solution enhancement may depend on a business function being active, and it may not be present in every customer system. Document the dependency, and test header and item level separately in both VA01 and VA02.

  • Function group V09C, screen 1000
  • Existing enhancement implementations
  • Table control line attributes
  • Modification versus enhancement

Item category versus schedule line category after a plant change (ref 71)

The poster in ref 71 derives the item category VBAP-PSTYV from a custom table when VBAP-WERKS changes. The logic sits in USEREXIT_MOVE_F8ELD_TO_VBAP. A manual plant change works. An ABC/ATP plant switch does not: the availability check runs only for the original item category, and the old schedule line data in MVERF is later used to overwrite the newly determined schedule line category from RV_SCHEDULING_TYPE_DETERMINE.

The underlying issue is ordering. The schedule line category depends on the item category, and the ATP check consumes schedule line data. If PSTYV is changed after the check has run, the cached results are stale. A late user exit therefore cannot fully fix it.

The sensible direction, which the post's analysis points to, is to set the item category earlier than the availability check, or to force a re-determination of the schedule lines after the change. This is a suggestion, not a verified fix. Trace with a watchpoint on VBAP-PSTYV and on the MVERF entries to see where they are written and consumed in the ABC flow.

The thread has no answer. Treat any fix as release-specific: check for standard BAdIs or events before the availability check, and confirm the behavior on your S/4HANA release, since changing standard structures such as MVERF directly would be a modification.

  • USEREXIT_MOVE_F8ELD_TO_VBAP
  • VBAP-PSTYV and VBAP-WERKS
  • MVERF
  • ABC/ATP plant switch
  • Schedule line determination order

Remote access to classic dynpro flow logic: ADT versus RFC (ref 100)

Ref 100 is a well-documented gap report. On S/4HANA 2023 (SAP_BASIS 758) and 2025 (816), the ADT discovery document at /sap/bc/adt/discovery has no collection for classic screens. A where-used on a PBO module returns screen 1000 of function group V09C as FUGR/PS with a /sap/bc/adt/vit/wb/... URI, but the author found no source endpoint behind it.

Over RFC the author lists three function modules. SVRS_GET_VERSION_DYNP_40 is RFC-enabled and returns flow logic in D022S_TAB. IMPORT_DYNPRO returns only the header (D020S) and fields (D021S). RPY_DYNPRO_READ returns everything but is not RFC-enabled.

The diagnostic order is reusable. First check the discovery document for a matching collection. Then use where-used to obtain object URIs and see whether they resolve. Finally compare function modules by RFC-enabled flag and by which table parameters they fill. Check the RFC flag yourself in SE37, since I only have the author's statement.

No answer is given, so as a team default, use SE80 or SE51 for flow logic and treat the RFC route via SVRS_GET_VERSION_DYNP_40 as a read-only workaround. The author notes it is a version-management function, so validate that it returns the active version.

Mid-level When do you override eDocument type or invoice type with the EDOC_ADAPTOR_CLOUD BAdI in S/4HANA Cloud Public Edition rather than use configuration?

Configuration first. The standard determination uses customizing such as 'Assign eDocument Type to Accounting Document Type/Billing Document Type/Delivery Type'. Ref 85 advises searching SAP Notes and checking whether source-application customizing can separate the cases before writing code. The BAdI is a last resort: IF_EDOC_ADAPTOR_CLOUD~CHANGE_EDOCUMENT_TYPE changes CV_EDOC_TYPE from IS_SOURCE_DATA, IV_SOURCE_KEY and IV_SOURCE_TYPE. Methods like CHANGE_INVOICE_TYPE (ref 107) are currently limited to France according to the post, and GET_VARIABLE_KEY (ref 83) changes the key used for customizing lookup. A wrong value can silently select the wrong number range or document type, which has compliance impact. Use Developer Extensibility, filter by country, and test in the tenant.
