Deep dives

The most valuable technical posts, explained.

BAPIs with ROLLBACK WORK inside a RAP unmanaged save

In RAP the framework owns the LUW. In the save sequence (finalize, check_before_save, adjust_numbers, save) COMMIT WORK and ROLLBACK WORK are forbidden. A BAPI that reaches ROLLBACK_CHECK in LV50IF01 and runs ROLLBACK WORK therefore raises BEHAVIOR_ILLEGAL_STATEMENT. This happens only on business-error paths, which is why the happy path looks fine.

The post's options: (A) call the BAPI via sRFC DESTINATION 'NONE' in the action handler (interaction phase), then BAPI_TRANSACTION_COMMIT or BAPI_TRANSACTION_ROLLBACK. This gives clean messages from the return table, but the commit is outside the RAP LUW. (B) keep the BAPI in save with pre-checks (ENQUEUE_EVVBLKE, MARV, MARD/MCHB). Unanticipated errors such as a missing OKB9 account assignment still dump. (C) cl_bgmc_process_factory with IF_BGMC_OP_SINGLE_TX_UNCONTR runs after commit in its own transaction, but it is asynchronous, and a controlled operation would hit the same ROLLBACK problem.

The trade-off is consistency against feedback. A is synchronous with real messages, but you must handle partial states, for example a BAPI success followed by a failure later in your own flow. C suits a case where the user can accept eventual status, with a status field and retry. The post gets no official answer, so test any choice for lock handling and failure recovery.

  • sRFC DESTINATION 'NONE'
  • bgPF uncontrolled operation
  • BAPI_TRANSACTION_COMMIT

Rebuilding approval history from change documents

EKKO and EBAN hold only the current release state (FRGZU). History lives in change documents: CDHDR (objectclas, objectid, username, udate, utime) joined to CDPOS (tabname, fname = 'FRGZU', value_new). Object classes are EINKBELEG for PO/LTA and BANF for PR. The report derives the release level by counting 'X' in the new value, for example with count( val = value_new sub = 'X' ).

The UI is one CL_SALV_TABLE. Hotspot columns DOCNO and SOURCE are set with if_salv_c_cell_type=>hotspot, and a handler on link_click either drills down one level or pops a history stack. Helper columns stay in the table but are hidden with set_visible( abap_false ).

Pitfalls: FOR ALL ENTRIES returns everything if the driver table is empty, so guard it. Confirm change documents are written for the object. The excerpt is truncated and has typos, so test before reuse.

Choosing the right extension point per inbound channel

The supplier invoice question shows a recurring Public Cloud problem. The same business object can be created via UI, EDI or A2A API, and each path may call different extension points. LOG_EDI_MM_INVOICE_CE_MAP targets B2B/EDI. The MRM_*_DATA_MODIFY_CE BAdIs (MRIS, MRDC, ERS) did not fire for the poster's tests, and the post does not say whether they were tested on the A2A path.

A practical method: confirm the channel, check the released BAdI list in ADT for that object, set a breakpoint or trace in the implementation, and run the exact channel. If none fires, the requirement may need a different mechanism, such as custom-field propagation through the API or a side-by-side approach. The post does not name the A2A API or the custom-field mechanism, so this is a method and not a solution.

Senior Why does a BAPI that issues ROLLBACK WORK dump when called from the save method of an unmanaged RAP BO, and how would you handle it?

In RAP the framework controls the LUW, and COMMIT WORK and ROLLBACK WORK are not allowed in the save sequence. A BAPI such as BAPI_OUTB_DELIVERY_CONFIRM_DEC reaches ROLLBACK_CHECK in LV50IF01 on business errors and executes ROLLBACK WORK, which raises BEHAVIOR_ILLEGAL_STATEMENT. Options are to run the BAPI in a separate session via sRFC with DESTINATION 'NONE' in the action handler, with explicit BAPI_TRANSACTION_COMMIT or ROLLBACK, or to run it after commit in a background process using bgPF. The sRFC route gives real messages but commits outside the RAP LUW. bgPF is asynchronous, so you need status and retry handling. Pre-checks reduce but cannot remove the risk of dumps.

Mid-level How do you reconstruct who released a purchase order and when, since EKKO only holds the current status?

Use change documents. Read CDHDR for objectclas EINKBELEG (PO, LTA) or BANF (PR) and the object ID, which gives username, udate and utime. Join CDPOS on the change number with fname FRGZU and the relevant tabname to get the new release value. The release level can be derived by counting 'X' in the new FRGZU value. Resolve full names from USER_ADDR. Check that change documents are actually written for the object, and when using FOR ALL ENTRIES, guard against an empty driver table because it would select all rows.

Architect A team wants an LLM to query S/4HANA data through a custom MCP server. What architecture and security concerns would you raise?

Direct SQL on HANA tables bypasses ABAP authority checks and CDS access control, so correct DB privileges do not give business-level authorization. It can also raise support and upgrade questions, which should be confirmed against current SAP statements. I would prefer released APIs, OData or CDS services with access control, exposed as narrowly scoped, predefined MCP tools rather than AI-generated SQL. Keep tools read-only where possible, log calls, and propagate the end user's identity instead of a technical user. Separate the three layers explicitly: database privilege, application authorization and the tool contract.
