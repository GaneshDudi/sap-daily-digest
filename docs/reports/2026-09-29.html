CONVERT_CURRENCY() in SQLScript and the HDI synonym pattern

CONVERT_CURRENCY() is a built-in SQLScript function. Use it instead of joining TCURR yourself and reimplementing rate selection. The parameters are AMOUNT, SOURCE_UNIT, TARGET_UNIT, REFERENCE_DATE, CLIENT, SCHEMA, CONVERSION_TYPE and ERROR_HANDLING [10].

CONVERSION_TYPE (M/P/B) controls how the exchange rate is selected. The function reads the currency customizing tables (TCURR, TCURF, and related tables). In an HDI container you cannot read those tables directly. You reach them through synonyms such as TCURR_CV_SYN and TCURF_CV_SYN. That is the main setup step in XSA, HANA Cloud and Datasphere [10].

Unit-of-measure normalization is a separate step, using the UMREZ/UMREN factors. A pricing model can therefore normalize both currency and unit in one pipeline. For ABAP developers, the same function fits AMDP methods on HANA. In CDS you would normally use the currency_conversion function instead. This is my inference; the source covers SQLScript only.

Word documents from ABAP Cloud with Content Controls and Custom XML

The usual approach to .docx output is to build or patch OOXML in ABAP, which is fragile. This method reverses it. The template is a normal Word file whose Content Controls are bound to a Custom XML Part. At runtime ABAP builds the data XML and swaps exactly one file inside the ZIP container. Word does the rendering when the document is opened [14].

Because only one part changes, the risk of corrupting the package is small. The approach uses only released APIs on S/4HANA Cloud Public Edition. That matters under ABAP Cloud rules, where you cannot rely on unreleased ZIP or XML utilities. A repository app lets business users upload and manage templates without a developer.

The author lists specific OOXML pitfalls and says the approach does not work for Excel [14]. The excerpt does not give the code. To teach it, you would reproduce the ZIP replacement yourself, using cl_abap_zip if it is released in your system (verify in ADT).

Diagnosing OData V2 CSRF 403 and lost $batch child rows

Two threads report 403 'CSRF token validation failed' although the token is sent. In BAS Preview, GET requests work and the POST fails. The response header X-CSRF-Token: Required is returned, the useBatch: false model setting is in use, and the same app works when deployed [28]. On the QRE system, several existing services began failing on $batch POSTs on 28 Sept, while the token fetch succeeds [30]. Neither thread gives a root cause.

A practical order of checks: confirm the token is fetched from the same host and session that later sends the POST (the ARBE cookie is missing in [28]). Compare the fetch and POST request headers. Check for a proxy or a session change between the two calls. Then check the Gateway side (SM59, /IWFND/ERROR_LOG, ICF/session settings) and any recent transports or kernel changes. These are suggestions, not findings from the threads.

The F2551 thread is a different problem: 'Scoring is not a deferred group' during submitChanges means the child entity was not in a deferred batch group, so the rows were left out of the changeset. A related LOAD_PROGRAM_INTF_MISMATCH dump in IF_MDQ_DS_TYPES had been fixed earlier [76]. Compare the console warning, the $batch payload and ST22 together.

Senior An OData V2 POST returns 403 'CSRF token validation failed' although the request carries a token. How do you investigate?

First establish scope. In the BAS Preview case only the POST failed and GET worked, and the deployed app worked [28]. In the QRE case many services failed at once from a specific date [30]. Compare the token fetch with the POST: same host, same session cookies, and the same token value. A missing session cookie or a proxy in between can make the server reject a token it issued. Check for changes on the Gateway side, such as configuration, transports or kernel, using /IWFND/ERROR_LOG. Test the same call outside the browser to separate a client problem from a server problem. Do not conclude 'known defect' without evidence, because neither thread has a confirmed cause.

Architect How would you expose RFC-enabled function modules to an AI agent safely?

Do not give the agent open RFC access. The pyrfc-mcp pattern places a policy-controlled layer between the agent and SAP [5]. It restricts which function modules can be discovered and called, handles transactions explicitly, limits response size, and writes an audit log of each call. On the ABAP side, use a dedicated technical user with a minimal authorization profile (S_RFC and the application authorization objects). That user is the real boundary, because the MCP layer only adds control. Prefer read-only or wrapper function modules, so the agent never calls a BAPI that commits changes directly. Test with the synthetic demo mode before connecting a real system.
