Deep dives

The most valuable technical posts, explained.

FOR ALL ENTRIES vs CTE, join and internal-table SQL source

FOR ALL ENTRIES IN @lt_vbak has two well-known hazards. If the driver table is initial, the restriction is dropped and the statement reads without the corresponding condition, so you need an IF lt_vbak IS NOT INITIAL guard. It also removes duplicate rows from the result set, which costs extra processing and can change the result if you expected duplicates.

The alternatives in the discussion are a CTE with WITH +open_orders AS ( ... ) SELECT ... INNER JOIN vbap, a plain join when both sides are in the database, and SELECT ... FROM @lt_vbak AS o INNER JOIN vbap (7.52+), which uses an internal table as a data source. The CTE and join push the work into a single database roundtrip. The internal-table source still ships the table to the database, so large tables can cause memory pressure, as the post notes.

The post says joins and FAE are not semantically identical when the driver set comes from separate logic. An inner join with an internal table does not deduplicate the way FAE does, so you may need DISTINCT or a prepared driver table. Claims in the post such as FAE being obsolete in ABAP Cloud and a 5,000–10,000 batch size have no source and should not be taught as fact. Measure with ST05 or SQL Monitor.

Debugging OPEN DATASET failures in background jobs

Two posts describe a CSV written with OPEN DATASET, TRANSFER and CLOSE DATASET that appears in AL11 when run in foreground and does not appear in a background job under a batch user. Neither shows code or a sy-subrc value. The post text does not give a cause. The areas worth checking are general ABAP knowledge, not from the posts.

First, check sy-subrc after OPEN DATASET, and use the MESSAGE msg addition to capture the OS message. Write path, sy-subrc and message to the job log. Second, the batch user needs authorization object S_DATASET for the path and activity. Third, the job may run on a different application server than the one where you looked in AL11, so check the target server in SM37. Fourth, use logical file names (FILE, FILE_GET_NAME) instead of hard-coded physical paths, so the path resolves per system.

The lesson for trainees is that file I/O must report failure explicitly. Without checks, a failed open looks like a successful run.

  • OPEN DATASET ... MESSAGE
  • sy-subrc checks
  • S_DATASET authorization
  • Job target server in SM37
  • Logical file names

CDS view vs SE16N on simplified tables: how to test the claim

The post claims a custom CDS view over simplified ECC tables (MBEWH, ANEK, ANEP) returns stale data, while SE16N shows live S/4HANA figures, and that CDS bypasses table redirection. The excerpt has no evidence, so treat it as a hypothesis to test.

A sandbox test: select from the table in SE16N and in a custom CDS view, then run both with an ST05 SQL trace and compare the statements and plans. Check what object each actually reads. Check whether the target tables are replaced by compatibility views or redirection, and whether the data is expected to exist in the old table at all in S/4HANA. Identify which result is correct before concluding anything about redirection.

The practical rule that comes out regardless is to read released CDS views or the new data model objects for a simplified area rather than the legacy table, and verify against the simplification documentation.

Interview questions

Grounded in today's material. Open each one to see a model answer.

Mid-level A report uses FOR ALL ENTRIES and sometimes returns far too many rows in production. What is the likely cause, and how would you fix and modernize the code?

The likely cause is an empty driver table. With FOR ALL ENTRIES, an initial driver table causes the read to happen without the restriction that depends on it, so it can return a large result. The fix is an IF driver IS NOT INITIAL guard. FAE also removes duplicate rows from the result, which adds overhead and can change semantics. To modernize, use a join or CTE (WITH +name) when the data is in the database, or SELECT FROM @itab AS alias INNER JOIN on 7.52+ when the driver is an internal table. Be careful that a join does not deduplicate like FAE, so you may need DISTINCT. Large internal tables passed to Open SQL can cause memory pressure, so I would verify with ST05 or SQL Monitor.

Architect In a CJ20N save BAdI, BAPI calls fail because of enqueue locks. A colleague proposes writing directly to PRTE. How would you evaluate that?

A direct write to PRTE bypasses SAP's consistency logic for scheduling data, so I would treat it as high risk and not accept it without evidence that it is supported. The BAPIs fail in the save BAdI because the project objects are locked by the same transaction, and the save LUW is not finished. I would look for a supported route inside the project update logic, such as changing the data structures the BAdI exposes, or a call that runs after the LUW commits, for example an asynchronous or update-task call that runs once the locks are released. I would also check the BAdI choice: the author notes WORKBREAKDOWN_UPDATE~AT_SAVE gets an empty IT_WBS_ELEMENT when only header dates change. Any approach needs testing for locking and rollback behaviour, and the claim that PRTE rows are not created for new WBS elements should be verified.
