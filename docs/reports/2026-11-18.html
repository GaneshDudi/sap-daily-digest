Deep dives

The most valuable technical posts, explained.

Active-table growth in managed RAP BOs with draft

In a managed RAP BO with draft, the draft table holds in-progress edits and the standard draft cleanup removes stale drafts. When a draft is activated, the data is written to the active table, and nothing in the framework removes it later. Ref 99 reports exactly this: finished rows accumulate in the active table.

The author considers two options. The first is deleting at the end of the process inside the BO implementation (for example in the saver or an action). The second is a periodic job that deletes finished rows after a retention period, in packages with COMMIT WORK. The post does not mention it, but SAP data archiving (archiving objects, SARA) is also a candidate.

Deleting in the save sequence couples business logic to data disposal. It also bypasses retention and audit rules, and rows may be referenced by other documents. A separate job is easier to govern, can be restarted, and keeps the transactional path small. Before deleting, check references, reporting needs and legal retention. The post asks for an SAP-documented pattern, and the text offers none, so this remains a design decision.

Cached CSRF tokens in CPI with retry on expiry

The CSRF handshake is a GET with header X-CSRF-Token: Fetch, and the token is read from the response header. Fetching it per message doubles calls. Ref 28 caches the token in a Data Store and refreshes it on a timer. Because the observed lifetime was 20 to 35 minutes rather than 60, a timer alone was unreliable.

The healing step handles an expiry response from ECC (typically HTTP 403 with a token-required message). The iFlow re-fetches the token, updates the cache and repeats the call, so the sender sees no failure. The excerpt gives no script or iFlow steps.

Design points to settle: how concurrent executions share the cache, whether several messages refreshing at once is acceptable, a hard retry limit of one so a persistent 403 is not looped, and how to test by forcing a 403. Token validity is also often tied to the session cookie, so the cookie should be cached together with the token. That last point is general knowledge, not from the post.

  • X-CSRF-Token: Fetch
  • Data Store caching
  • Retry on 403
  • Bounded retries
  • Concurrent refresh

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A managed RAP BO with draft keeps finished rows in the active table forever. How would you handle it?

First clarify that draft cleanup only removes stale rows from the draft tables, so the active table needs its own retention approach. I would avoid deleting in the saver or end of the process flow, because it mixes business logic with disposal and bypasses retention and audit rules. Preferred options are SAP data archiving where an archiving object is justified, or a scheduled retention job that deletes in packages with COMMIT WORK after a defined retention period. Before deleting, check references from other documents, reporting needs and legal retention. The job should be restartable and log what it removed. The post itself found no SAP-documented pattern, so this is a design choice that should be agreed with the business.

Question: Handling finished rows in the active table of a custom manag
Senior How would you design CSRF token handling in a CPI iFlow posting to an ECC OData service at volume?

Fetching a token per message doubles the calls. I would cache the token in a Data Store, refresh it on a timer, and on an expiry response (typically HTTP 403 with a token-required message) re-fetch, update the cache and retry once. The timer interval must be shorter than the real lifetime, which one author observed at 20 to 35 minutes rather than 60. I would also consider the session cookie, which the token is often bound to. Concurrent executions should not all refresh at once, so the refresh should be serialised or tolerated explicitly. Retries must be capped to avoid loops, and the expiry path should be tested by forcing a 403.

Architect A BAS app must call S/4HANA Private Cloud through a BTP Destination without basic authentication. How do you approach the design?

Start by deciding whether the call needs a technical identity or the end user's identity, because that determines the OAuth grant and the whole setup. For a technical user, a client-credentials style flow is the usual candidate. For user-level authorisation, a user-propagating flow is needed. On the ABAP side, check the OAuth 2.0 client registration, scopes, the communication arrangement and the trust setup. On the BTP side, set the destination authentication type, token service URL, client ID and secret. Draw the token flow and note where each secret is stored. The source post gives no configuration, so these points are the checklist to verify against SAP Help.
