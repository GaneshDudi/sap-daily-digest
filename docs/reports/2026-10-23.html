Deep dives

The most valuable technical posts, explained.

Why pushing a LEFT OUTER JOIN into UNION branches changes the result

The correct query builds a UNION ALL of CENTRAL_DELIVERIES and REGIONAL_DELIVERIES (a CTE), then does a LEFT OUTER JOIN from ORDERS filtered to region_id = 2. The expected result is 3 rows (ORD300, ORD400 with NULL, ORD500). In the execution plan the UNION ALL runs first, so the filtered order IDs do not reduce the scans of either delivery table.

The tempting fix is to duplicate the filtered ORDERS and the LEFT OUTER JOIN into each UNION branch. Each branch then preserves every unmatched order on its own. An order that has a delivery in only one table gets a real row from one branch and a NULL-extended row from the other. The result has duplicates (6 rows per the text; the post's own table lists five, so recheck the example).

The optimizer may apply semi-join reduction in simple cases, but this is cost-based and not guaranteed. The same issue applies to a CDS association that targets a UNION view. The post does not show the corrected version, so these options are not from the source. Candidate alternatives are to filter the union by order ID, or to split the logic into an inner join plus a separate handling of unmatched orders. Whatever you choose, compare row counts against the baseline on a small data set.

  • UNION ALL below a join
  • LEFT OUTER JOIN preserves unmatched rows per branch
  • Semi-join reduction is cost-based
  • CDS association to a UNION view
  • Verify rewrites by row count

CPI encoding: bytes versus strings

The poster needs an ISO-8859-1 file on SFTP. A Groovy step that sets the encoding, an XSL conversion and adapter header settings all left the output as UTF-8. A forum reply says script steps reinterpret the string and that the encoding is handled at the adapter level.

The underlying point is that a Java String has no encoding. Encoding applies when it becomes bytes. If a script converts the body to bytes in the target charset, a later step or the adapter may decode or re-encode them, so you must check where the final bytes are produced. The post does not confirm a working solution, so test in a lab with a character such as an umlaut and inspect the file in a hex view.

For class use: build a flow that writes a message with special characters, try the script-based and adapter-based approaches, and compare the hex output of each. Record which step finally decides the encoding.

  • String vs byte[]
  • Adapter-level encoding
  • Groovy script step
  • Hex verification of output
  • UTF-8 vs ISO-8859-1

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A CDS view joins ORDERS to a UNION ALL of two delivery tables with a LEFT OUTER JOIN, and it is slow. A colleague proposes moving the filter and the outer join into each UNION branch. What happens?

The result changes. Each branch does its own LEFT OUTER JOIN, so each one keeps every unmatched order. An order with a delivery in only one table gets a real row from that branch and a NULL-extended row from the other, and orders with no delivery get a NULL row from both. The result has more rows than the original and contains duplicates. In the original plan the UNION ALL runs before the join, so the order filter does not reduce the delivery scans. The optimizer may apply semi-join reduction in simple cases, but that is cost-based. I would verify any rewrite by comparing row counts on a small data set, and look for a form that restricts the union by order ID without changing the outer-join semantics.

Senior In RAP, what is the difference between exclusive and collaborative drafts, and what problem arises when the draft owner is unavailable?

With exclusive drafts, only the user who created the draft can modify, activate or discard it. With collaborative drafts, other users can work on it, but they must be invited through the Share draft action. The problem is that if the owner is absent, an exclusive draft is stuck. A collaborative draft needs invitations, which become impractical across many users. I would not assume a standard takeover feature exists; I would check the RAP draft documentation and the behaviour of the standard app in question. As a design choice, I would decide at modelling time whether the business object needs collaborative editing. I would also define who may discard drafts and how administrators clean up orphaned ones.

Class idea

Safe CDS tuning: UNION views, outer joins and result verification

Today's SAP post shows that a plausible push-down of a filter and outer join into UNION branches silently changes results. Experienced developers need a repeatable way to check that a performance rewrite is equivalent.

  1. Review the setup: ORDERS, CENTRAL_DELIVERIES, REGIONAL_DELIVERIES
  2. Correct query: UNION ALL then LEFT OUTER JOIN, expected 3 rows
  3. Read the plan: where the UNION ALL runs and what the filter does not reduce
  4. The naive push-down and why unmatched rows are duplicated
  5. Semi-join reduction: cost-based, not guaranteed
  6. The same effect with CDS associations to UNION views
  7. Equivalence testing: row counts and EXCEPT-style comparisons
  8. Candidate alternatives and how to judge them

Hands-on exercise: In ADT, create the three tables with the sample data and a CDS view entity over the UNION. Write the baseline query and the naive push-down variant, run both through a small ABAP Open SQL report, and compare row counts. Then propose and test your own equivalent rewrite, proving it matches the baseline result.
