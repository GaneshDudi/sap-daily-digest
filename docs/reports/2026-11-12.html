Today's material is mostly community questions with no answers. The ABAP-relevant ones share a pattern: a hook (BAdI, substitution exit, BAPI) does not behave the way the developer assumed. Examples are PR validation that does not fire for PM and SD generated requisitions, a batch classification BAdI that does not fire after production goods receipt, and BAPI_PO_CHANGE returning success without changing the address. The only release-style item is a migration guide for the Usage Records API, from v1 to OData V4 v2.

Deep dives

The most valuable technical posts, explained.

Tracing which creation channels call your BAdI (PR validation case)

The posts about PR validation describe a BAdI (ME_PROCESS_REQ_CUST / MM_PUR_S4_PR_CHECK) that fires for ME51N, ME52N and Fiori, but not for PRs generated from PM or SD orders. The posts do not give a cause, so what follows is a method, not a confirmed answer.

Start by listing every channel that creates a PR: interactive UI, PM order components, SD-generated requisitions, and any BAPI or background job. For each channel, set an external breakpoint in the BAdI method (or in the call site of the BAdI) and run the scenario. If the breakpoint is not reached, look at the call stack from the source document to see which API creates the requisition. That API decides which hooks are available.

Keep two concerns apart. Validation must run before the document is saved and be able to reject it. A workflow event, such as a manually raised event for BUS2105 via SWE_EVENT_CREATE_IN_UPD_TASK, only starts a process after the fact. It cannot replace a check. If a single MM-level hook does not cover a channel, the options are to place the check on the source object side or to check again at a later stage. Weigh these against duplication of logic and the risk of missing a path.

For class use, give students the same scenario in a sandbox and ask them to produce a table: channel, API called, hooks reached, where the check should live.

  • BAdI call path vs creation channel
  • Validation vs workflow event
  • External breakpoints and call stack
  • Source-side vs target-side checks

Verifying change BAPIs: BAPI_PO_CHANGE returning success with no effect

The poster reports BAPI_PO_CHANGE returning an empty RETURN table while the delivery address does not change, but only when EKPO-ADRNR is blank. The post does not show the parameters, so the cause is not established. The point to teach is how to verify a change BAPI.

A robust pattern: fill both the data structure and its corresponding X-structure with the right item key and flags, call the BAPI, then loop over RETURN for types E, A and also W. An empty RETURN is not proof of success. Then call BAPI_TRANSACTION_COMMIT with WAIT = abap_true on success, or BAPI_TRANSACTION_ROLLBACK otherwise. Finally read the PO back (BAPI_PO_GETDETAIL or a select on EKPO and the address data) and compare to the intended value.

For a blank address number, a plausible hypothesis is that the BAPI has no existing address record to update and so needs a different input for creating one. Treat this as something to test in a system, not as a known fact. Compare the BAPI's behaviour with ME22N for the same PO, and check the BAPI documentation and SAP notes.

In a controlled approval process, the read-back check should be part of the program, so that a silent no-op raises an error instead of marking the change as done.

  • RETURN table evaluation (E, A, W)
  • X-structures / change flags
  • BAPI_TRANSACTION_COMMIT with WAIT
  • Read-back verification

Moving from a proprietary REST API to OData V4: the Usage Records v2 checklist

The Usage Records v2 migration is a compact example of what changes when a proprietary REST API becomes OData V4. List parameters filter, sort, pageSize and pageNumber become $filter, $orderby and $top. The total count moves from the x-count header into the body as @count when $count=true is used. Collection filters use lambda operators such as customReferences/any(c:c/typeCode eq 'SYSTEM_TYPE').

Breaking changes need a field-level map: userTechnicalId to technicalResourceId, isAssigned to assigned, changedAt to modifiedAt, changedBy to modifiedBy, subscriptionNumber to subscriptionDocumentNumber. Single upsert changes from POST /usage-records to POST /UsageRecords/upsertByLogicalKey with the payload wrapped in a value object. A client that ignores the renames will not necessarily fail loudly, so contract tests against v2 are advisable.

Batch now uses standard multipart/mixed. A changeset gives all-or-nothing behaviour and is optional, so requests outside a changeset are processed independently. The same concepts apply to RAP-based OData V4 services you build in ABAP, so this is a useful reference for what consumers expect. The source post stops before the pagination section, so check the full documentation there.

Senior A custom PR validation BAdI works in ME51N and Fiori but not for PRs generated from PM orders. How do you investigate and decide where the check belongs?

First I list every channel that creates a PR: interactive UI, PM order components, SD-generated requisitions, and any BAPI or batch. For each one I set an external breakpoint in the BAdI method and run the scenario. Where it is not reached, I read the call stack from the source document to find which API creates the PR, because that API determines which hooks exist. I then separate validation from workflow: a check must run before save and be able to reject the document, while an event such as one raised for BUS2105 only starts a process afterwards. If no MM-level hook covers a channel, I place the check on the source object side or at a later stage, and accept the cost of keeping logic in two places. I document the channel-to-hook mapping so new channels are tested.

Mid-level BAPI_PO_CHANGE returns an empty RETURN table, but the delivery address is not changed. How do you make such a call reliable?

Architect How would you design an idempotent payment initiation across several CPI iFlows, given that a Data Store Get followed by Write is not atomic?

The duplicate check must be a single atomic operation, not a read followed by a write. I would use a store with a unique constraint on the Payment Request ID, where the insert itself is the check, so one of two concurrent requests fails. A single-writer queue is an alternative. I would keep an explicit state machine such as INITIATED, PENDING, SUCCESS and FAILED, and persist the state before calling the gateway. For uncertain outcomes, such as the gateway charging but CPI missing the response, I call the gateway inquiry API before any retry. Webhooks are handled idempotently by keying on the transaction reference and ignoring state transitions already applied. I would not assume CPI Data Store gives transactional concurrency guarantees without confirming this in the documentation, and I would add reconciliation, retention and monitoring.
