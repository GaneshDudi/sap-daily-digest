Deep dives

The most valuable technical posts, explained.

Containing non-catchable dumps in ABAP mass-change jobs

The question in ref 56 describes a background job looping over sales orders with SD_SALESDOCUMENT_CHANGE. A TRY...CATCH cx_root handles class-based exceptions. An ASSERTION_FAILED runtime error raised in SAP's own class code (CL_SD_SLS_TRANS_MGR) ends the session. The poster says it cannot be caught; verify this against the keyword documentation for ASSERT and checkpoint groups, since behaviour depends on how the assertion is activated.

Whatever the catchability, the design answer is to limit the blast radius. Options: one background job per order or batch, or CALL FUNCTION ... STARTING NEW TASK with RECEIVE so a dump in the called task is reported to the caller as a system failure (verify on your release). Commit per document so completed orders stay committed.

Add a custom status table keyed by sales document (status, timestamp, message). On rerun, skip finished orders and mark the failed one as 'dumped' so it is not retried endlessly. This makes the job idempotent and restartable.

In parallel, analyse the dump in ST22 and search SAP Notes for the class and method. A dump in standard code is usually a data inconsistency or an SAP defect, and a wrapper cannot fix that.

  • Class-based exceptions vs runtime errors
  • STARTING NEW TASK / RECEIVE ... FAILED handling
  • Per-document commit
  • Idempotent restart table
  • ST22 and SAP Note analysis

BAPI_SALESORDER_CHANGE: building a safe reason-for-rejection update

Ref 40 shows a .NET RFC client setting REASON_REJ 'Z1' on item 002000. The first defect is visible in the code: CreateFunction(" ") should use BAPI_SALESORDER_CHANGE.

The BAPI needs matching structures: ORDER_ITEM_IN carries ITM_NUMBER and REASON_REJ, and ORDER_ITEM_INX carries ITM_NUMBER, UPDATEFLAG 'U' and REASON_REJ 'X'. ORDER_HEADER_INX gets UPDATEFLAG 'U'. The posted code does this pairing correctly.

The KK 049 'Enter costing sheet' message means the item is being re-processed through costing or pricing, not just getting a reason code. Check that Z1 is a valid rejection reason in customizing, and whether the item's pricing or costing procedure is complete. Use BAPI_SALESORDER_SIMULATE or a test order to see whether the reason code change triggers it.

The code only collects RETURN messages of type E and A. Collect all types, including W and I, to see what the BAPI reports before the error. Commit with BAPI_TRANSACTION_COMMIT WAIT = 'X' only when no E or A message exists, and call BAPI_TRANSACTION_ROLLBACK otherwise. Within the .NET connector, keep the BeginContext/EndContext scope around both the change and the commit.

  • ORDER_ITEM_IN / ORDER_ITEM_INX pairing
  • UPDATEFLAG
  • RETURN message handling
  • BAPI_TRANSACTION_COMMIT / ROLLBACK
  • BAPI_SALESORDER_SIMULATE
Discussion: Consult about BAPI_SALESORDER_CHANGE to update REASON_REJ

CAP error contract: req.error forms and sap-messages localization

Refs 90 and 92 are two reproducible reports on @sap/cds 10.1.1. In ref 90, req.error(409,'PROBE_CONFLICT') returns details[].code "409", while req.error({status:409, code:'PROBE_CONFLICT'}) returns the key. The i18n text resolves in both. req.reject has the same effect at the top level.

Practical rule: use the object form wherever clients or tests depend on a stable code. Add a test asserting details[].code against the OData V4 error body (MULTIPLE_ERRORS with details[]).

In ref 92, req.info, req.warn and req.notify write to the sap-messages header in the server default language, ignoring Accept-Language, while req.error bodies are localized. The documented behaviour says they should accept the same arguments as req.reject and use the Accept-Language header. The reported workaround is cds.i18n.messages.at(key, req.locale, args) before calling req.info.

Both posts have no answer from SAP in the supplied text, so treat them as reported behaviour and re-test on your own @sap/cds version.

  • req.error positional vs object form
  • details[].code
  • sap-messages header
  • cds.i18n.messages.at
  • req.locale

Grounded in today's material. Open each one to see a model answer.

Senior A background job calling SD_SALESDOCUMENT_CHANGE in a loop is terminated by an ASSERTION_FAILED dump inside a standard SAP class, despite TRY...CATCH cx_root. How do you make the job resilient?

A CATCH on cx_root covers class-based exceptions. A runtime error such as a failed assertion ends the session, and whether it is catchable depends on how the assertion is raised, so I would check the ABAP keyword documentation instead of assuming. I would not rely on in-process handling. First, I would analyse the dump in ST22 and search SAP Notes for the class and method, because it points to a data or code defect in standard. Second, I would isolate processing: separate jobs per batch of orders, or asynchronous tasks with CALL FUNCTION STARTING NEW TASK and RECEIVE, where a dump in the task shows up as a system failure to the caller (verify on the release). Third, I would commit per document and keep a status table keyed by sales document so a rerun skips finished orders and flags the dumped one. This makes the job restartable and limits the damage.

Mid-level You set REASON_REJ with BAPI_SALESORDER_CHANGE and get 'Enter costing sheet' and 'Sales document was not changed'. How do you build and debug the call?

First verify the structures. ORDER_ITEM_IN holds ITM_NUMBER and REASON_REJ, and ORDER_ITEM_INX holds the same item number, UPDATEFLAG 'U' and REASON_REJ 'X'. ORDER_HEADER_INX also needs UPDATEFLAG 'U'. Then check that the function name is actually BAPI_SALESORDER_CHANGE, since the posted client code used a blank name. The costing message means the item went through pricing or costing re-determination, so check the reason code in customizing and the item's costing or pricing setup. I would read the full RETURN table, not only types E and A, and run BAPI_SALESORDER_SIMULATE to see if the change itself triggers the error. Commit with BAPI_TRANSACTION_COMMIT only when no E or A message exists, otherwise call BAPI_TRANSACTION_ROLLBACK.

Class idea

Resilient mass-change programs: BAPI discipline, dumps and restartability

Today's forum questions show a batch killed by a dump in standard code, BAPI_SALESORDER_CHANGE costing errors with a code defect, and 261 batch selection surprises.

  1. Catchable exceptions vs runtime errors; reading ST22
  2. Correct BAPI structure use: data and INX pairing, full RETURN evaluation
  3. Commit and rollback strategy per document
  4. Process isolation: separate jobs, STARTING NEW TASK with RECEIVE
  5. Status table design and idempotent restart
  6. Simulating and testing before real changes
  7. Passing explicit values (for example BATCH) instead of relying on defaults

Hands-on exercise: In ADT, write a report that changes the rejection reason on a list of test sales orders with BAPI_SALESORDER_CHANGE.
