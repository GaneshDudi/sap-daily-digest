Capturing standard ALV data with CL_SALV_BS_RUNTIME_INFO, and why it fails

The pattern is: call CL_SALV_BS_RUNTIME_INFO=>set( display = abap_false metadata = abap_false data = abap_true ), run SUBMIT report ... AND RETURN, then call get_data_ref( IMPORTING r_data = lr_data ) inside a TRY block catching cx_salv_bs_sc_runtime_info. The ALV is meant to be intercepted before display and the data table handed back.

It breaks when the report still builds control framework objects. The FAGLB03 poster gets DC006 'GUI cannot be reached' in a background or submitted context, which means the report's path does not fully honour the runtime-info switch. The FAGLL03H poster gets the other failure: the report creates more than one ALV instance, and R_DATA references the layout-side table, not the line items. Neither thread has a confirmed fix.

The first post also has plain code defects. The rbukrs range is typed TY_RANGE_RACCT (a range of SAKNR) where a company code range is needed. ASSIGN lt_data_ref->* TO <any_table> lacks a sy-subrc check. CORRESPONDING into a local structure only works if field names match the ALV output.

For teaching: first fix the types and checks, then inspect lt_data_ref in the debugger to see which table you got. If the report cannot be intercepted cleanly, the more robust route is to read the underlying data source (CDS view, function module or tables) instead of scraping the UI. That is a design suggestion, not something the posts confirm.

  • SUBMIT ... AND RETURN
  • DC006 control framework error
  • Typed range tables
  • ASSIGN with sy-subrc check
  • Multiple ALV instances in one report

Session-bound CSRF tokens in CPI calls to ABAP OData V4

ABAP Gateway ties the CSRF token to the server session. A GET with x-csrf-token: Fetch returns the token and session cookies. The POST is only accepted if it sends the token and the cookies from that same session. Postman keeps a cookie jar, so it works. A CPI HTTP adapter call does not carry cookies between steps unless you pass them.

The posted workaround stores x-csrf-token and set-cookie as properties in Groovy (message.getHeaders(), message.setProperty(...)), then sets x-csrf-token and Cookie headers in a Content Modifier. The weak point is passing the raw Set-Cookie value. Set-Cookie includes attributes such as Path, HttpOnly, Secure and Expires. A Cookie request header should contain only name=value; name2=value2. If several Set-Cookie headers come back as a list, the code may also pick up only one or a flattened string. Header key case should be checked too.

Things to test, not confirmed by the thread: log the full header map in the Groovy script; build the Cookie string from name=value pairs of every Set-Cookie entry; confirm GET and POST use the same host, path, client and user; reproduce with curl using -c and -b first. The response shows sap-usercontext and sap-XSRF_<SID>_<client> cookies, and a session cookie may also be needed. If the error persists, check the Gateway error log on the ABAP side.

  • x-csrf-token Fetch
  • Set-Cookie vs Cookie header
  • Session-bound token
  • Groovy Message API
  • /IWBEP/CM_V4H_RUN/042
  • curl cookie jar

ADT Extract Method and flow-change preconditions

Extract Method in ADT evaluates the selected range through a POST to /sap/bc/adt/refactorings with step=evaluate. The poster's selection includes SUBMIT fagl_account_balance ... AND RETURN and fails with 'Source contains program flow change by RETURN'. Tested on Eclipse 2025-09, ADT 3.52.3, backend 7.58 SP1.

The precondition has a sound basis: a real RETURN in extracted code would leave the new method, not the original routine, so behaviour would change. The open question is whether AND RETURN in SUBMIT, which only means the calling program resumes afterwards, is being matched as a flow change. The post does not say whether a newer release fixes this, so check ADT and backend release notes.

The workaround from the post works: comment out the SUBMIT, run Extract Method, then restore it manually and call the new method from the right place. For classes, use it to show how refactoring prechecks work and how to isolate such statements into their own method first.

Senior An iFlow in Cloud Integration fetches a CSRF token with a GET and the following POST to an ABAP OData V4 service fails with CSRF_Token_Missing. Postman works. How do you analyse it?

The ABAP CSRF token is bound to the server session, so the POST has to run in the same session as the GET. Postman keeps a cookie jar, whereas the CPI HTTP adapter does not carry cookies between steps by default. I would log the response headers from the GET and check every Set-Cookie value. Then I would build a Cookie request header from name=value pairs only, dropping attributes such as Path, HttpOnly and Expires. I would also confirm that host, client and user are identical in both calls and that the Fetch header was sent correctly. I would reproduce with curl and a cookie jar before changing the iFlow. If it still fails, the Gateway error log on the ABAP side shows the cause.

Mid-level ADT Extract Method refuses a selection containing SUBMIT ... AND RETURN. Why do such preconditions exist, and how do you proceed?
