Using ABAP Cloud readiness checks as a learning loop

With the ABAP Cloud Developer Trial unavailable, the post [7] proposes using an existing S/4HANA 2023 development system, where ABAP Cloud rules are active. The author wrote a classic-style program, ran the ABAP Cloud readiness check and got 23 findings. After rewriting it the ABAP Cloud way, the check gave 0 findings and the program ran. The post doesn't list the findings, so this is a method, not a catalogue.

To reproduce it, build a report that deliberately breaks the rules. Use a direct SELECT on a non-released table, an obsolete statement, a call to a non-released function module or class, and classic list output. Run the readiness check, group the findings by cause, and fix each group. Typical fixes are released CDS views or released APIs instead of tables, and released classes instead of unreleased ones. These are standard ABAP Cloud practices, not details from the post.

The value is that findings become a measurable exercise: the finding count falls as each category is fixed, and the end state is a program that runs under ABAP Cloud language version rules. Use a sandbox package, not a productive one.

Destination properties and HTTP headers in ABAP Cloud

The question [71] describes a destination with Additional Properties such as URL.headers.irpa-api-key and URL.queries.environmentId. In CAP these are added to outgoing requests automatically. In ABAP Cloud RAP the developer reads the key and sets it with set_header_field on an if_web_http_client request before calling execute( i_method = if_web_http_client=>post ).

The thread asks for a standard API to read the additional properties and a way to avoid duplicating the secret in ABAP code. No answer is given, so don't assume automatic propagation exists. Check the current documentation for the destination-to-HTTP-client path your release uses.

Whatever mechanism is used, the design goal is clear: the secret lives in the destination or a communication arrangement, and not in the source code, constants or a custom table.

Verifying what a BAdI or released API actually exposes

Two questions show the same trap. In [19], BAdI PRCG_DOC_ITEM_CONDITION_AMOUNT provides only SUPPLIER and PLANT, but the pricing rule needs the sending storage location. A SELECT on the order fails because it isn't saved yet at pricing time. In [39], CustomerRequirementType is missing from the I_SalesDocumentItem OData V2 entity.

The check order is the same each time. First read the interface or signature of the extension point, then the CDS view in ADT, then the service's exposed properties in $metadata. A field can exist in the CDS view and not in the API. If the view has it, an extension or a custom projection with a service definition and binding is the route [39]. If the BAdI doesn't pass the data, any alternative must be verified against SAP documentation, because [19] has no answer.

The older user exit question [50] follows the same pattern: find the calling program with where-used, then check copy control before coding.

  • Custom projection and service binding

Mid-level The ABAP Cloud Developer Trial is unavailable. How would you prepare a team to learn ABAP Cloud restrictions using an existing S/4HANA 2023 system?

An S/4HANA 2023 development system already has ABAP Cloud rules active, so it can serve as a practice environment. I would create a sandbox package and write a classic-style program with typical violations: direct selects on non-released tables, non-released API calls and obsolete statements. Then I would run the ABAP Cloud readiness check and record the findings. The team fixes them by category until the count reaches zero, as one blog went from 23 to 0. The fixes use released CDS views and released APIs. Finally, confirm the program runs under the ABAP Cloud language version. Use a sandbox package so nothing productive is touched.

Senior Async inbound SOAP calls to S/4HANA Cloud return success but the data isn't replicated. How do you diagnose and monitor this?

Async inbound SOAP returns an HTTP acknowledgement before business processing, so the response says nothing about the result. Processing errors are logged in AIF, which end users don't see by default. I would use the Message Dashboard to find the failed entry. For proactive alerts, assign an AIF recipient to the user in Assign Recipients to Users (F2949), using the namespace and recipient from the API's documentation, for example /CMDPR and CMD_PRODUCT for the product master service. Then set the interface notification to 'E-Mail for Every Single Error'. The user also needs a valid e-mail address in Maintain Business Users. Synchronous services return errors in the response and don't need this.

Architect A BAdI doesn't pass a field you need, and a released OData API lacks a field. How do you decide where to change?

I first confirm what each layer provides. For the BAdI, I read its interface signature. In the STO pricing case, PRCG_DOC_ITEM_CONDITION_AMOUNT gives only SUPPLIER and PLANT, and the order isn't saved, so selecting from the database fails. I would look for another extension point or data source, and verify it against SAP documentation. For the API, I open the CDS view in ADT and compare it with the service's $metadata, because a field can exist in the view and be absent from the API. If the view has it, I would use an extension or a custom projection with a service definition and binding. If it doesn't, the field isn't available at that layer. I don't design before this check.
