Grouping RAP actions with UI annotations

The grouping is purely a UI concern. In the metadata extension or CDS annotations you add one line item of type: #FOR_ACTION_GROUP with a label (here 'Status') and an actionGroupId (here 'GRP1'). Then you add actionGroupId: 'GRP1' to each #FOR_ACTION line item that has its dataAction and label (Approve, Reject, cancel).

The behaviour definition does not change. The actions stay declared as action (features: instance) Approve parameter ZA_APPROVE_PARAM result [1] $self and similar. Because they use features: instance, the feature control logic still decides per row whether each entry in the dropdown is enabled.

The source post calls these factory actions in its intro and headings, then says they are instance-bound non-factory actions. Use that as a teaching point. A factory action creates new instances (factory action), while these return $self. The post shows no action implementation, tests or screenshots, so verify the rendering in Fiori Elements yourself.

A behavioural check is another option: a unique index should reject a duplicate insert on the key fields. This is an inference, not something stated in the post.

Mid-level How do you group several RAP actions into one dropdown in a Fiori Elements list report, and does it affect the behaviour definition?

You add a @UI.lineItem entry of type #FOR_ACTION_GROUP with a label and an actionGroupId. Then you add the same actionGroupId to each #FOR_ACTION line item that references the action through dataAction. The behaviour definition is not changed, because grouping is purely presentation. Enablement is still driven by the action's feature control, for example features: instance, so each entry can be enabled or disabled per row. This is different from a factory action, which creates new instances, whereas instance actions here return $self.

Senior A table has a new unique secondary index in a BTP ABAP trial, and ADT shows no index list. How would you separate repository checks from database checks?

First confirm the definition: the index must be in the activated table or index object with the intended fields. That is the repository view. Second, the physical state sits in the HANA catalog, and ABAP Cloud restricts direct database access, so what is possible in a trial is limited. In the source question, Open ABAP Development Object rejects type INDX and Index Overview shows only general table properties. A behavioural test is possible: insert two rows with the same key fields and expect the second to fail. That test shows uniqueness is enforced but not the index's physical structure. State this limit when you report the result.

Architect What controls would you put in place before letting an AI agent edit ABAP objects through MCP in ADT?

Separate read operations from write operations. Read and search tools carry little risk. Write, activate and publish operations should happen only in a development system, on a dedicated transport, with a named developer responsible. Generated code goes through peer review and ATC, including Clean Core checks, before release. Restrict the agent's authorizations so it cannot release transports. Log what the agent changed. The source post only describes the capability in its abstract, so these controls are design recommendations, not features of the tool.
