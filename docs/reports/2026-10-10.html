Implementing EDOC_ADAPTOR_CLOUD restrict_cancel safely

The BAdI EDOC_ADAPTOR_CLOUD is available in S/4HANA Cloud Public Edition under Developer Extensibility. The relevant method is if_edoc_adaptor_cloud~restrict_cancel. It receives the eDocument and the source document key and type, and returns the decision in the changing parameter cv_restrict. Setting it to abap_true blocks cancellation, and abap_false allows it.

The implementing class must implement if_badi_interfaces and if_edoc_adaptor_cloud, and provide is_relevant. The BAdI offers filters for country and a generic filter, so the implementation should apply only to the intended scope instead of every eDocument. The post gives the spot name inconsistently (ES_EDOCUMENT_CLOUD and ES_DOCUMENT_CLOUD), so confirm it in the system.

The main risk is business consistency. The standard text 'Unable to cancel document; Cancel related eDocument first' exists because an accepted eDocument with a cancelled invoice is inconsistent with the legal record. Decide per country and eDocument status which states may allow cancellation before coding, and prefer a credit memo or further invoice where the process requires it.

Choosing an extension point when a BAdI is single-use

DIP_AD010007 has no Multiple Use flag and SAP's implementation /CPD/PWSSE_BPM_RRB already uses it. A second active implementation is therefore not possible. The post does not say which release applies.

A sound check order is: confirm multiplicity in the BAdI definition (SE18), list active implementations (SE19), and search for SAP Notes on the intent of the restriction. Then evaluate the classic exit EXIT_SAPLAD15_015 (include ZXAD1U06) and check how it relates to the BAdI in the processing sequence. The post leaves that execution order unanswered.

A classic exit is not automatically clean-core compliant. Without SAP confirmation, such as a Note or a support answer, treat it as a risk to document, not as a supported path.

The author confirmed that $metadata loads in a browser and that the XML downloaded, so the document itself looks fine. The likely causes are in how the generator fetches or parses it, for example authentication, redirects or the destination. That is an inference, not confirmed by the post.
