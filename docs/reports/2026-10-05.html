Chaining agents into workflows instead of monolithic agents

The post says agents with many tools and long instructions fail unattended: wrong paths, retry loops, poor auditability and high model cost. The proposed pattern is a declared workflow with a main line, one fan-out step, branches and a join. Steps are agent steps or deterministic ones (condition, transform, http, python) that need no LLM. Why it matters: It draws a clear line: code for rules, LLMs for judgment, with cheaper models for simple steps. This is a useful design test for any automation, including ABAP background jobs.

Building an MCP server from an OpenAPI spec in Integration Suite

The blog creates an MCP server artifact in Integration Suite (Integration Cell runtime) via Design → Integration Packages → Add MCP Server. The connection type is HTTP Endpoint with an OpenAPI specification, uploaded as a file. The spec must be OpenAPI 3.0. The SuccessFactors spec from SAP Business Accelerator Hub is 2.0 (Swagger), so it has to be converted first.

The example covers the Company Car domain in OData v2, with three layers. Reference data is AllowedModels, RecommendedVendors and LeaseServiceProvider. Policy is BenefitCompanyCar. Employee transactions are CompanyCarEnrollment and CompanyCarClaim. Tool discovery yielded 12 tools. The MCP Configuration tab then lets you inspect Tools, Resources and Prompts, including their input and output schemas, and manage Policies. The virtual host path (for example <Virtual Host>/sfsf) decides where the endpoint is hosted.

The main lesson is that the tool description is what the agent reads when choosing a tool. The blog recommends natural-language descriptions over technical entity names. The same applies to your own OData services: poor $metadata and annotations will likely produce poor tools. The post does not cover ABAP-backed services, so that part is an inference.

Deterministic steps vs LLM steps in agent workflows

The workflow post defines step kinds. Agent steps have a model and a timeout (600s in the example). Deterministic steps are condition (rules with continue/stop), transform (JSON path, regex, template, truncate), http (via a BTP destination) and python (subprocess, 60s timeout in the example). The structure is a main line, at most one fan-out step that must sit on the main line, branches and a join.

Handoff is plain text. Templates use {{text}}, {{item.<path>}}, {{json.<path>}} and {{source.<name>}}, which are substituted with no expression language. Branches have a key and description, and the description is appended to the fan-out instruction as decision rules.

The example, sap-config-baseline, reads config, scores it against a baseline and writes a report. The scoring is a condition, not a judgment, so no LLM is needed. The rationale is reliability, auditability and cost: use cheap models for reading and expensive ones only where judgment is required.

Senior Why might an unattended agent workflow use deterministic steps instead of letting one agent handle everything?

A single agent with many tools and long instructions can choose wrong paths, loop on retries, and is hard to audit. It also pays model cost on every step. Splitting into a workflow lets rule-based logic, such as comparing a score with a baseline, run as a condition or transform step with no LLM. That makes the outcome reproducible and traceable. Agent steps are kept for judgment, and cheaper models can handle simple reading tasks. The same principle applies in ABAP: do not put deterministic rules inside a non-deterministic component.
