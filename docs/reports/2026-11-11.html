The most valuable technical posts, explained.

Making `with unmanaged save` safe: error handling in `save_modified`

With with unmanaged save in a managed BDEF, RAP still handles the transactional buffer, CRUD flow, locking and authorization. Only persistence moves into the saver class, which inherits cl_abap_behavior_saver, in save_modified. The post ref 61 calls ZBAPI_SALESHEADER_CREATE per created row in that method.

Three gaps in the post matter. First, ls_return (BAPIRET2) is overwritten on every loop iteration and never inspected, so a failed BAPI looks like a success. Second, the update and delete branches only fill lt_sales_update and lt_sales_delete, so those operations are silently lost. Third, nothing is returned through reported or failed.

A sketch of the fix: in the create loop, read the BAPI RETURN after each call and check for type E or A. If it is an error, add the row key to failed-saleshead and a message to reported. Then implement the update and delete branches. Note that the save phase is late: save_modified is called in the save sequence after the interaction phase, so a failure there is not an ordinary validation. Do validations in the interaction phase with validations or determinations, so that save-time failures are rare. The post also leaves out etag handling and number assignment for vbeln, and the check of the table's last_changed_at field, which is not exposed in the CDS views.

Also decide where the BAPI is called. The post does it in save_modified. The teaching angle in the source suggests comparing save_modified with cleanup_finalize. Keep database commits out of the saver, because RAP controls the commit.

  • `with unmanaged save`
  • `cl_abap_behavior_saver`, `save_modified`
  • BAPIRET2 check after each call
  • `reported`/`failed` propagation
  • Validation in the interaction phase, not in save

ABAP Unit inheritance and ADT run scope

Ref 42 gives a minimal reproduction. An abstract test class ltc_type_unsigned_int is declared ABSTRACT FOR TESTING RISK LEVEL HARMLESS DURATION SHORT, with test_2 FOR TESTING RAISING cx_static_check in its PROTECTED SECTION. A final subclass ltc_unsigned_int4 inherits it with an empty implementation. A third class ltc_dummy has its own test method.

Running with the cursor on ltc_unsigned_int4 and Ctrl+Shift+F10 executes ltc_dummy as well. Running the same class from Project Explorer runs only that class. The post suggests the editor action does not recognise a class with no test methods of its own, and falls back to a wider scope. That is a hypothesis, not a confirmed root cause. The reporter used ABAP platform 7.58 SP1, Eclipse 2025-09 and ADT 3.52.3, and no fix or Note is mentioned.

Practical points: inheriting test methods from an abstract superclass is a legitimate pattern for running one contract against several implementations. Until the behaviour is fixed, start the run from Project Explorer, or select the method in the Outline. To test whether a method of your own in the subclass changes the scope, add a trivial FOR TESTING method as a diagnostic step. Treat that as an experiment to try, not a documented workaround.

  • ABSTRACT test classes with FOR TESTING
  • Inherited test methods
  • Editor versus Project Explorer run scope
  • Minimal reproduction

Regression analysis with SAT: the SAP TM cockpit case

Ref 83 is a useful template for reporting a performance regression. It has before and after timings (under 10 seconds versus over 3 minutes), the same selection and similar data, and an SAT trace with one dominant class, /SCMTMS/CL_Q_SUPERCLASS. The standard check message /SCMTMS/AC 099 was not raised.

A structured approach: first confirm that the data volume and the selection are really comparable. Then take an SAT trace with aggregation by call hierarchy, not only by hit list, to see which callers drive time in the query superclass. In parallel, take an SQL trace (ST05) or the HANA SQL plan cache to separate ABAP processing time from database time. The post does not say which of the two dominates, so the cause is open. Check SAP Notes for the TM query framework on 2025 FPS02, and compare buffer and cache behaviour after the upgrade.

The lesson for developers: a hot spot in a framework superclass is only a starting point. It identifies the framework layer, not the faulty code. Document the evidence before opening a ticket.

  • SAT call hierarchy versus hit list
  • ST05 / SQL plan cache
  • Before/after baseline
  • Framework hotspot versus root cause

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior You use `with unmanaged save` in a managed RAP BO to call an existing BAPI. What must the saver implement to make it production-safe?

The framework still handles the transactional buffer, locking and authorization, so the saver only replaces persistence in save_modified. For every created, updated and deleted instance, call the BAPI or function module and inspect its RETURN table, not only the last row's result. On type E or A, fill failed and reported for the affected key so the consumer does not see a false success. Do not let BAPIRET2 be overwritten inside a loop. Implement update and delete branches explicitly, because collecting rows in internal tables without writing them loses data. Do not commit inside the saver, because RAP controls the commit. Do validation earlier, in the interaction phase, so save-time failures are rare.

Mid-level An ABAP Unit class inherits all its test methods from an abstract FOR TESTING superclass. In ADT, running it from the editor also runs another test class. How would you analyse and work around it?

First reproduce it minimally: abstract superclass with the test method in a PROTECTED section, empty final subclass, plus an unrelated test class. Then compare run entry points. In the reported case, Ctrl+Shift+F10 in the editor ran both classes, while Project Explorer ran only the intended one. The reporter used ADT 3.52.3 and ABAP platform 7.58 SP1, and no root cause or fix is documented. Plausibly the editor action does not find test methods declared directly in the subclass and widens scope, but that is a hypothesis. The practical workaround is to run from Project Explorer. Also test whether adding a method in the subclass changes the behaviour, and check newer ADT or backend versions before reporting it.
