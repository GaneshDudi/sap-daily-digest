Deep dives

The most valuable technical posts, explained.

Filter-style BAdI in EWM: steering quant selection with /SCWM/EX_CORE_RMS_DETERMINE

The post implements /SCWM/IF_EX_CORE_RMS_DETERMINE~DETERMINE to restrict which quants the warehouse task creation may use. The inputs are is_ltap and it_qmat. The output is et_qmat_cus, flagged with ev_set. The logic reads the ship-to party from the outbound delivery via /SCWM/CL_DLV_MANAGEMENT_PRD=>GET_INSTANCE( )->QUERY with is_include_data-head_partyloc. It then finds packaging specifications under condition type 0OBD, using pak_ship_to and pak_matid, with validity checked against a GET TIME STAMP FIELD value.

The HU side reads /SCWM/HUHDR (huident, ps_guid) with FOR ALL ENTRIES into a sorted table with a unique key. Only quants whose HU packspec matches the customer's spec are returned. Lookups in a sorted table are efficient, but FOR ALL ENTRIES needs a guard for an empty driver table. Without it, the select reads everything. It also removes duplicates, which can hide rows if the selected fields are not unique.

The key design point is the fallback. When nothing matches, the method returns without setting ev_set, so standard behaviour applies. That means a customer could still receive the wrong pack size, which is the original problem. Decide explicitly whether to fall back to standard selection or to block the task, and log it either way.

Caveats from the post: the code has VERIFY markers on party role type, the head_partyloc flag and party_role, plus artefacts like @LC _cond_typ that stop it compiling. It reads the non-standard table /1CN/CPSSAPOBD03 directly. Packspec content tables are generated and can differ between systems, so a released API is safer where one exists. Treat the post as a sketch.

  • /SCWM/EX_CORE_RMS_DETERMINE
  • Packaging specification condition 0OBD
  • FOR ALL ENTRIES with empty-table guard
  • Sorted table with unique key
  • Fallback to standard when ev_set is not set
  • Avoiding direct reads of generated tables

Controlling manual pricing conditions in billing (VF02): where to look

The question (S/4HANA 1709, delivery-related billing with VTFL, pricing type G) asks for per-condition-type control: discounts locked, packing charges editable. The post names no mechanism, so the following are control points to check, not a confirmed solution.

The first place is the condition type definition, where the manual-entry setting limits whether a condition can be entered or changed by hand. The second is the pricing procedure, where step control for the condition type can affect changes. Third, the pricing type in VTFL decides how pricing is carried from the order into billing (G in this case), and it applies to the whole item, so it cannot separate discounts from packing charges. The fourth is an enhancement in billing or pricing that rejects changes for named condition types.

Because the requirement is per condition type, configuration alone may not be enough. If one condition type serves both purposes, it may need splitting. Test each option on 1709 before choosing, and check side effects on delivery-related billing, such as re-pricing when the document is saved.

  • Manual condition control in billing
  • Copy control VTFL pricing type G
  • Pricing procedure step control
  • Per condition type enhancement as fallback

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior You implement a filter-style BAdI that restricts candidate records, and no rule matches. How do you decide the fallback behaviour?

First, find what the business wants when no rule matches: standard behaviour, or a hard stop. In the EWM example (ref 15), an unset ev_set means standard picking applies, so a wrong pack size can still go out. If the rule is a compliance requirement, raise a message or block creation. If it is a preference, fall back and write an application log entry so exceptions can be reviewed. Document the choice and test the no-match case explicitly. Silent fallback hides defects, which is why it should be a conscious decision.

Mid-level What are the risks of FOR ALL ENTRIES in a BAdI that runs during warehouse task creation, and how do you reduce them?

If the driver table is empty, FOR ALL ENTRIES selects all rows without the WHERE condition on it, so guard with an IS NOT INITIAL check. It also removes duplicate rows from the result, so include enough key fields to keep rows distinct. Large driver tables are split into several database statements, which costs time in a performance-sensitive process. Sort or sort-and-dedupe the driver table first. Put results in a sorted or hashed table with a suitable key for lookups. Where possible, use a join or a CDS view instead. Also avoid reading generated tables such as /1CN/ ones directly if a released API exists (ref 15).

Senior A user needs to create RFQs from purchase requisitions programmatically and cannot find a BAPI. How do you proceed?

Start by searching the BAPI Explorer by business object for the PR and the RFQ, and check released APIs for your release. Then trace what the standard RFQ-from-PR transaction calls and whether it offers a reusable function module or class. Search purchasing BAdIs in SE18/SE19 for hooks that fit the process. If no suitable interface exists, build a wrapper that reads the PR, filters the allowed document types, and calls the most stable available API. Isolate it behind your own class so it can be replaced when SAP provides a supported API. Document the release, since availability differs between versions (ref 23).
