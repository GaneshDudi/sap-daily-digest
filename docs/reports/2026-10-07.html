Deep dives

The most valuable technical posts, explained.

Managed RAP with unmanaged save orchestrating standard BOs

The question in ref 34 uses a custom managed BO with with unmanaged save. A determination calls MODIFY ENTITIES OF i_purchaserequisitiontp to create purchase requisitions, using %cid and %cid_ref to link header and items. A custom table zpr_request stores the mapping.

The same technique applies to i_purchaseordertp if that interface is available in your release. Check the released BDEF and its supported operations. A PO needs a supplier, purchasing organisation and so on, so the input mapping and the standard validations will differ from a PR. These details come from general RAP knowledge, not from the post.

Points to teach: %cid is a temporary key valid within one request. After the call, %pid/%tky and CONVERT KEY (as used in the post) map to the final keys. Handle failed and reported from the called BO, and be careful about where in the RAP interaction/save phase you call another BO's MODIFY, because the save sequence has restrictions on modifying and committing. Test this on your own system.

  • MODIFY ENTITIES
  • %cid / %cid_ref
  • %pid / %tky
  • CONVERT KEY
  • failed / reported handling

Silent BAPI success: verifying BAPI_BUPA_ROLE_ADD_2 in S/4

In ref 58, BAPI_BUPA_CREATE_FROM_DATA creates a partner and BAPI_BUPA_ROLE_ADD_2 with FLCU01 returns without error, yet BP does not show the role. The post gives no cause.

A systematic check: read the whole RETURN table, including warning and info types, not just type E. Confirm BAPI_TRANSACTION_COMMIT runs after the sequence, and that the partner is committed before the role call. Then check the database tables for the role directly (BUT100) to separate display problems from persistence problems. Also check whether customer data in S/4 requires the CVI link and further customer-specific data. That last point is general S/4 knowledge, not stated in the post.

A robust pattern is to wrap the calls, collect all messages, and read the partner back after commit. For larger migrations, consider the released BP APIs or the BP maintenance classes rather than old BAPIs.

Fiori Elements multi-select on object page tables for RAP actions

Ref 93 asks how to replace radio buttons with checkboxes for line items so that approve/reject runs on selected items only. The post does not name a solution.

In Fiori Elements, table selection mode is typically set in the app's manifest.json table settings, not in the RAP behavior definition. Actions are exposed through @UI.lineItem entries of type #FOR_ACTION on the child entity. For the action to run per selected row, define it as an instance action on the child entity in the behavior definition. This is general Fiori Elements/RAP knowledge, so verify it on your release.

Teaching exercise: compare what happens when the action is defined on the header versus the item, and how selected keys arrive in keys in the action implementation.

  • @UI.lineItem #FOR_ACTION
  • Instance actions on child entity

Interview questions

Grounded in today's material. Open each one to see a model answer.

Mid-level A BAPI_BUPA_ROLE_ADD_2 call returns no error, but the customer role FLCU01 does not appear in transaction BP. How do you investigate?

First I read the complete RETURN table, including warnings and information messages, because success can hide messages. Then I check that BAPI_TRANSACTION_COMMIT is executed after the partner creation and the role call, since the BAPIs do not commit by themselves. I verify persistence by reading the partner back in a new LUW and checking table BUT100. I also consider whether the customer role in S/4 needs additional data, such as the customer-vendor integration link. I would build a wrapper that collects all messages and fails the batch record when the read-back does not show the role. For larger migrations I would compare with the released BP APIs.

Question: Create a customer in S/4 with BAPI
Senior In a managed RAP BO with unmanaged save, how do you create a purchase requisition through a released standard BO, and what pitfalls apply when extending that to purchase orders?

You use MODIFY ENTITIES OF the released BDEF, passing the create data with %cid for new instances and %cid_ref to link child items to the header. After the call you evaluate failed and reported, and map temporary keys to the final keys with CONVERT KEY or the %pid/%tky handling, then persist the mapping in your own table. For purchase orders, first check that a released interface exists in your release and which operations it supports. PO data requirements differ, for example the supplier is required, and the standard BO runs its own validations. You must also respect the RAP save-sequence restrictions on where such calls and commits are allowed. I would test the sequence thoroughly, including failure handling, before relying on it.

Question: Managed RAP application to create PurchaseOrder
Architect A customer is moving from S/4HANA on-premise to Public Cloud and relies on BTEs and function modules for custom logic. How do you approach it?

I start with an inventory of all custom code and exits, and classify each by business purpose. For each, I check whether a released extension point, key-user extensibility, or a developer extensibility option in Public Cloud exists. Where none exists, as seen in the payment advice case and the CO11N validation case, I look at process alternatives such as configuration, output or form settings, or side-by-side extensions on BTP. I bring those gaps to the project early as scope and cost items. I do not promise to recreate the classic code. Sometimes a business process change is the correct answer.
