Consuming CDS views safely: visible in ADT versus released

The question about I_NotificationCause.NotificationCauseText shows a common trap. A view can be opened in ADT and return data without being released for use. Release state is shown in ADT on the API State tab of the view's properties, and the released-objects list is the authoritative check. The post says the view is not released for key-user or developer extensibility, so building on it carries upgrade risk.

A practical approach: first check whether a released view or API exposes the same text, for example a released text association or a related released view in the same business area. If none exists, the options are a custom CDS view on the underlying tables with an explicit risk note, or asking SAP for a release. The post names no released replacement, so treat any specific alternative as unverified.

For teaching, have students open an I_ view, read its release contracts, and test a custom view that selects from it. Then show how the check differs on-premise versus ABAP Cloud, where use of unreleased objects is restricted by the language version. The post is silent on the exact release, so keep the discussion general.

  • API state / release contract
  • Released vs visible objects
  • Key-user and developer extensibility
  • Custom view risk trade-off

Diagnosing a failing A_OutbDeliveryHeader create in API_OUTBOUND_DELIVERY_SRV

The poster POSTs to A_OutbDeliveryHeader with to_DeliveryDocumentItem, referencing the sales order via ReferenceSDDocument and ReferenceSDDocumentItem, and gets LE_SHP_ODATA_API_OD/001 'Wrong input parameters'. They claim PlannedGoodsIssueDate, StorageLocation and Batch are not accepted at creation.

The error text is generic, so check the facts rather than guess. Read $metadata and look at sap:creatable and sap:updatable on the properties being set. Then find the detailed error in /IWFND/ERROR_LOG on the hub, filtered by timestamp or transaction ID; SAP Note 1797736 covers Gateway error analysis. Separate header from item fields and retest by removing one field at a time.

In the standard flow, item data such as quantity and storage location derive from the referenced sales order, which is why overriding them at create may be rejected. Whether a second step (a PATCH after create) is allowed is not confirmed by the post, so test it rather than assert it.

  • $metadata creatable/updatable annotations
  • /IWFND/ERROR_LOG
  • Reference-based document creation
  • Isolating fields by bisecting payload

Agent loop and guardrails in the ABAP AI SDK posts

The posts describe a loop: an external LLM proposes a tool call, ABAP executes it against the live system, and the result feeds the next step. The excerpt stresses execution controls but does not show them, so the following is design guidance, not a description of the SDK.

Sensible controls for such a loop: whitelist the tools, default to read-only, run authority checks under the calling user, and log every call. For state, one post credits an SDK message container with carrying context across turns and mentions compaction, which presumably condenses older turns. Another keeps curated knowledge in Z tables and avoids caching live configuration values, which prevents stale answers.

The ABAP-specific questions to explore are where history is held between WebSocket messages, how a background run relates to the open connection, and what is lost on compaction. Confirm each against the SDK documentation before teaching.

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A report needs a text field that exists only in an unreleased standard CDS view. How do you proceed?

First confirm the release state in ADT on the view's API State, since being visible and returning data does not make it part of the supported contract. Then look for a released view, API or association that exposes the same text. If none exists, I weigh a custom CDS view on the underlying source against upgrade risk, and document that risk explicitly. I would also raise a release request with SAP. In ABAP Cloud scenarios the language version restricts unreleased objects anyway, so this route may not be available. The decision should be recorded and reviewed at each upgrade.

Mid-level An OData V2 POST to API_OUTBOUND_DELIVERY_SRV returns LE_SHP_ODATA_API_OD/001. How do you find the cause?

The message is generic, so I gather evidence. I read $metadata and check sap:creatable and sap:updatable on the properties in the payload. I open /IWFND/ERROR_LOG on the Gateway hub, filter by timestamp, and look for the detailed message; SAP Note 1797736 covers Gateway error analysis. I separate header and item fields and remove them one at a time to find which is rejected. Since item data in a reference-based create is derived from the sales order, I check whether overriding StorageLocation or Batch is allowed at create. If not, I test whether a later update is permitted rather than assuming.

Architect How would you design guardrails for an ABAP agent that queries live S/4HANA configuration through tools?

I would expose only whitelisted tools, each narrow and read-only by default. Every tool runs under the calling user's authorisations, with explicit authority checks, so the agent cannot see more than the user can. All calls and results are logged for audit. I would not cache current configuration values in agent memory, because they go stale; durable knowledge is stored separately and curated, as one post describes with Z tables. For multi-turn use, I need to know where conversation history lives and how compaction affects it. Write-capable tools need separate approval and are kept out of the first version.

Class idea

Diagnosing Released-API and OData Failures Without Guessing

Today's Q&A shows developers blocked by an unreleased CDS view and a generic OData create error, both solvable with a systematic checklist.

  1. Visible vs released: API State and release contracts in ADT
  2. Finding released alternatives for a needed field
  3. Decision path: custom view, risk note, release request
  4. OData V2 $metadata: creatable/updatable annotations
  5. Reading /IWFND/ERROR_LOG and SAP Note 1797736
  6. Bisecting a deep-insert payload
  7. Async APIs: acknowledgement vs outcome, correlation IDs

Hands-on exercise: In ADT, pick three I_ views and record each one's release state. For one unreleased view, find a released path to the same field or write a custom view with a documented risk note. Then call a released OData V2 service with a deliberately invalid field, locate the error in /IWFND/ERROR_LOG, and fix the payload using $metadata.
