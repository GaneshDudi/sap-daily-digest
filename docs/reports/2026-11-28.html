Designing a secure file download with RAP OData V4 and Edm.Stream

The post (ref 32) describes serving AL11 application-server files through a RAP OData V4 service that returns content as Edm.Stream. Only the abstract is available, so the code below is my own sketch of the pattern and not taken from the post. It is meant for discussion.

In RAP, a stream is normally modelled as a media property: an xstring content field annotated with @Semantics.largeObject (mimeType, fileName, contentDispositionPreference), plus a MIME type field. Reading the file means OPEN DATASET ... FOR INPUT IN BINARY MODE on a path your code builds. That is where the security risk lies.

The controls the post lists map to concrete checks. First, never accept a path from the client. Accept a key such as a logical folder ID and a file name. Resolve the folder from a configuration table. Second, validate the file name against a whitelist (no /, \, .., or control characters), then check that the resolved path still begins with the mapped directory. Third, check the file size before reading into an xstring, because large files exhaust memory. Fourth, call the authorisation check before opening the file. The post says this check is replaceable, so it would sit behind an interface.

In the ABAP standard, logical file names (transaction FILE, FILE_VALIDATE_NAME) are the usual way to constrain paths. The post does not say whether it uses them, so ask this when reviewing. Also ask whether DCL or a behaviour-level authorisation covers the entity, or only a custom class does.

  • Edm.Stream and @Semantics.largeObject in RAP
  • Path traversal validation
  • Configuration-driven folder mapping
  • Replaceable authorisation interface
  • OPEN DATASET in binary mode
  • File size limits before xstring read

Principal propagation in BTP destinations: reading the OAuth2SAMLBearerAssertion error

The question (ref 37) reports the error 'Cannot determine user to propagate for OAuth2SAMLBearerAssertion destination' from a BPA action calling SuccessFactors. The error text lists two remedies: provide a user_token JWT when retrieving the destination, or configure the destination with SystemUser.

With OAuth2SAMLBearerAssertion, the destination service builds a SAML assertion for a specific user and exchanges it for a token at the target system. It needs a user identity as input. If the call comes from a runtime that has no user JWT, such as a process started in a technical context, the service cannot build the assertion.

The post does not give the root cause. My inference is that the workflow runs without the Work Zone user's token, but this is unconfirmed. To narrow it down, check whether the process is triggered with the user's context, and whether the BPA action receives a user token at all.

The two remedies differ in meaning. A user_token keeps the real user, so SuccessFactors applies that user's permissions. SystemUser maps every call to one configured identity, which is simpler but loses per-user authorisation and audit. Choose based on the requirement, and verify against current BPA and destination service documentation.

  • OAuth2SAMLBearerAssertion
  • Principal propagation
  • user_token JWT
  • SystemUser destination option
  • BTP destination service

Two change requests, one include: a ChaRM sequencing problem

The post (ref 36) describes include ZINFE0003_XXX assigned to change request 6XX0000473, while 6XX0000888 needs the same object and will be transported first. The author asks whether to remove the object and reassign it, use a separate transport, or resynchronise tracking. There is no reply.

The underlying issue is that an ABAP object is locked by one open task or request at a time. ChaRM ties transports to change requests, so moving an object by hand can desynchronise the tracking. That risk is general. The post does not give the system landscape or transport state, so I cannot say which option is safe here.

The usual options are ordering the transports so the first one carries the older version and the second builds on it, or merging both changes into one request. Reassigning after work has started is the riskiest. Before acting, check the version history of the include and the status of both transports.

This is a good example to teach, but any step-by-step advice has to be checked against the project's ChaRM configuration and SAP documentation.

Senior You must expose files from AL11 through a RAP OData V4 service. How do you design it to prevent path traversal and unauthorised access?

I would model the content as a stream property using a largeObject annotation and return it as Edm.Stream. The client never sends a path. It sends a logical folder key and a file name. The backend resolves the folder from a configuration table. I validate the file name against a whitelist and reject separators and '..'. After building the full path I confirm it still lies inside the mapped directory. Logical file names with FILE_VALIDATE_NAME are an option for this. I check authorisation before OPEN DATASET, and check the file size before reading it into an xstring so memory is not exhausted. Direct access to the file outside the service must also be blocked at the OS and AL11 level.

Mid-level Two ChaRM change requests need changes to the same include, and the later-started one must go to production first. How do you approach it?

I would not start by removing the object from one request and adding it to the other, because that can desynchronise ChaRM tracking from the transports. First I check the status of both requests and transports and the version history of the include. Then I look at the sequencing options. One is to release the transports in an order where the later change builds on the earlier version. Another is to merge both changes into one change request. A third is to rebase the second change on the first. The decision depends on the landscape and project ChaRM settings, so I would confirm it with the change manager and SAP documentation. The aim is that no transport overwrites a newer version of the object.
