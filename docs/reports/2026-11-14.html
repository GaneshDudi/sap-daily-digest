Priority 1

PO quantity change audit report built on CDHDR/CDPOS

The custom report ZPO_QTY_CHANGE_REPORT lists EKPO-MENGE changes for POs created in a given year. It reads CDHDR and CDPOS with OBJECTCLAS = EINKBELEG, TABNAME = EKPO, FNAME = MENGE and CHNGIND = U. TABKEY is decoded as MANDT(3) + EBELN(10) + EBELP(5), so EBELN sits at offset 3 and EBELP at offset 13. VALUE_OLD and VALUE_NEW are text, and a helper moves a trailing minus to the front before conversion. Difference is old minus new, so a positive value means a reduction. Users are enriched via USR21 and ADRP, sorted tables with unique keys are used for lookups, FOR ALL ENTRIES is guarded against empty driver tables, and output goes through CL_SALV_TABLE.

Why it matters: It is a reusable pattern for audit reports on other fields such as price or delivery date. Two points need checking before reuse: the source is truncated at the selection screen, and the choice of date field for 'created in year' (AEDAT versus ERDAT) should be verified. Also confirm change documents are active for EINKBELEG.

Reading change documents: CDHDR/CDPOS join and TABKEY decoding

The report links CDPOS to CDHDR on OBJECTCLAS, OBJECTID and CHANGENR. For purchase orders the object class is EINKBELEG and the object ID is the PO number. Item-level quantity changes are filtered with TABNAME = 'EKPO', FNAME = 'MENGE' and CHNGIND = 'U' (update).

CDPOS stores the key of the changed row in TABKEY, a concatenated string. For EKPO it is MANDT(3) + EBELN(10) + EBELP(5), so the PO number is tabkey+3(10) and the item is tabkey+13(5). The post uses these offsets to split the key.

VALUE_OLD and VALUE_NEW are character fields. Quantities may carry a trailing minus, which does not convert directly, so the post tests lv_txt+lv_len(1) = '-' and moves the sign to the front with CONCATENATE '-' lv_txt INTO lv_txt before conversion. Difference is old minus new, so a positive result means the quantity was reduced.

For performance it uses FOR ALL ENTRIES only after checking the driver table is not empty, and holds lookups in SORTED TABLE ... WITH UNIQUE KEY objectclas objectid changenr so READ TABLE uses binary search. Users are resolved through USR21 and ADRP and output goes through CL_SALV_TABLE. Caveats: the source is truncated, CDPOS is a cluster-like large table on many systems, so test volume, and verify which date field defines the creation year. On S/4HANA, consider whether a CDS view or the standard change document read function modules fit better.

Principal propagation: logon tickets versus OAuth2 SAML Bearer

In PI/PO, principal propagation to the backend relied on SSO2 logon tickets. The post states that this does not apply to SAP Integration Suite Cloud Integration, which authenticates inbound XI calls through XSUAA using OAuth.

The proposed replacement is the OAuth2 SAML Bearer Assertion grant. A SAML assertion identifying the user is exchanged for an access token, and the identity is carried over the XI 3.0 protocol from the S/4HANA on-premise system. The post says it includes configuration steps, a simulation and limitations, but none of that was supplied.

For a class, the useful exercise is mapping trust objects on each side: identity provider, XSUAA, credential and destination setup, and certificates. Do not teach specific steps until the full article and SAP documentation have been checked.

Senior Why is FOR ALL ENTRIES risky and what guard is needed?

If the driver table is empty, FOR ALL ENTRIES ignores the WHERE condition on it and selects all rows, which can return a huge result. Always check the driver table is not empty first. Duplicate rows are removed from the result, so include the key fields you need to avoid losing data. On large tables like CDPOS, also check the selection is supported by an index. Where possible, a join or a CDS view is preferable on HANA.
