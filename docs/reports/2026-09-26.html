Draft Query Views: The RAP Security Gap Nobody Checks

Ref 9 exposes an architectural blind spot in RAP that catches out even experienced developers: DCL authorization checks defined via @AccessControl.authorizationCheck: #CHECK on your active CDS entity do not automatically apply to the corresponding draft persistence table. RAP's draft-enabled apps store in-progress edits in a separate draft table, generated alongside the active table, and by default that draft table has no independent access control layer. A user who cannot see or edit certain active records can still create, view, and edit a draft of those same records unless you explicitly close the gap.

The fix is a Draft Query View: a CDS view built specifically over the draft persistence, wired into the behavior definition via the query addition alongside use draft;. This gives you a second, independent point to apply @AccessControl.authorizationCheck — meaning your DCL role now protects both the active and draft states of the entity. Without it, the projection layer's authorization is effectively a facade during the edit-in-progress phase.

The post walks through a complete, non-trivial example: a Price Change Request app starting from the database table zaf_dt_pricerequ, through the interface CDS entity ZAF_I_PRICEREQU (carrying the @AccessControl.authorizationCheck: #CHECK annotation), the projection ZAF_C_PRICEREQDF (using provider contract transactional_query), and a behavior definition wiring in the standard draft actions — Activate, Discard, Edit, Resume, Prepare. Metadata extensions (@UI.facet, @UI.lineItem, @UI.identification) complete the Fiori Elements rendering.

For teams building transactional RAP apps with sensitive data — pricing, HR, credit — this is not an edge case. Any draft-enabled business object with row-level or field-level authorization requirements needs this pattern verified explicitly, because the framework will silently let it slide otherwise. Treat draft query views as a mandatory checklist item in RAP security reviews, not an optional hardening step.

  • Draft Query Views and the `use draft;` behavior directive
  • `@AccessControl.authorizationCheck: #CHECK` scope limitations
  • DCL (Data Control Language) and its boundary at the projection layer
  • Standard draft actions: Activate, Discard, Edit, Resume, Prepare

X.509 Certificate Authentication for the ABAP ODBC Driver: PEM vs PSE

Ref 34 is a dense, code-heavy walkthrough of certificate-based auth for the SAP ODBC driver — increasingly the default for password-less connections into ABAP systems, particularly on BTP. The core parameter is AuthenticationType=X509; once set, Uid becomes unnecessary because the certificate itself carries the identity. The driver supports two distinct certificate handling models, and confusing them is the most common configuration mistake: PEM, where the driver itself parses and manages the certificate material, and PSE (Personal Security Environment), the SAP-standard format managed at the OS level via sapcryptolib and the sapgenpse tool.

A critical, easy-to-miss detail: the TrustedCertificates and UserCertificates connection parameters work together as a combined set, but the driver only uses the *first* private key it encounters — if your connection string lists multiple certificates with private keys, only the first is honored. This has bitten teams who assumed multiple client certs could be chained.

Patch Level 33 is the milestone to know: it introduced file-path support for PEM certificates (previously you had to inline the full PEM content in the connection string, which broke under unixODBC's string length limits) and added support for encrypted private keys, with the decryption password passed via the standard Pwd parameter. For PSE-based setups, the driver defers entirely to OS-level credential management: it requires the SECUDIR environment variable pointing to the PSE store and a cred_v2 credential file, both provisioned via sapgenpse.

For any developer setting up secure external tool integration (BI tools, custom reporting, third-party connectors) into an ABAP system without embedding passwords, this is the reference architecture. Know which format your target environment expects before you start — retrofitting from PEM to PSE (or vice versa) mid-project means redoing your entire credential provisioning pipeline.

  • X.509 client certificate authentication via `AuthenticationType=X509`
  • PEM (driver-managed) vs PSE (OS-managed via `sapcryptolib`) certificate models
  • `TrustedCertificates`/`UserCertificates` parameter semantics — first private key only
  • Patch Level 33: file-path support and encrypted private key handling
  • PSE provisioning: `SECUDIR`, `cred_v2`, and `sapgenpse`

Joule Studio's JEV Model: Separating Judgment from Generation in Agentic AI

Ref 40 describes a production architecture pattern worth studying regardless of whether you use Joule Studio: separating the *generative* reasoning layer from the *decision* layer when an AI agent's output triggers a real side effect (in this case, releasing a payment). The invoice triage agent uses Claude for evidence gathering, tool orchestration, and natural-language explanation — the parts of the task that benefit from open-ended reasoning — but hands the actual release-or-hold decision to JEV, TypeSafe's constrained judgment model.

JEV exposes three primitives instead of free text: Choice (pick from a predefined option set), Score (rank against a rubric), and Noul (a calibrated yes/no probability). Crucially, JEV is trained with RLCD (Reinforcement Learning for Calibrated Decisions), which produces confidence scores derived from actual probability distributions — not a language model's verbal self-assessment of certainty, which is notoriously unreliable. The output of JEV is then passed to a plain Python wrapper that enforces the outcome deterministically before any state-changing call is made; the LLM never directly executes the side effect.

This three-layer separation — generative model for evidence and explanation, decision model for bounded judgment, imperative code for enforcement — is the practical answer to 'how do you let an agent make consequential decisions without letting it run wild.' The jl CLI supports this as a pro-code workflow: build and test locally in your own IDE (the post specifically uses Claude Code), then push to the Joule Studio landscape for validation, packaging, and deployment.

On the data side, the agent's memory is handled through SAP HANA Cloud's VECTOR_EMBEDDING and COSINE_SIMILARITY SQL functions, scoped by agentID and invokerID, so semantic retrieval only pulls relevant history into the prompt rather than replaying the full conversation — keeping both token cost and latency under control. For architects evaluating agentic AI for anything touching financial or irreversible actions, this pattern — generate, judge, enforce — is the one to bring to the design review.

  • Separating generative reasoning from constrained decision-making in agentic AI
  • JEV judgment primitives: Choice, Score, Noul
  • RLCD-calibrated confidence vs verbal LLM certainty
  • Deterministic outcome enforcement in code before side effects execute
  • Semantic memory scoping via `VECTOR_EMBEDDING`/`COSINE_SIMILARITY` in HANA Cloud

Architect Describe an architecture pattern for letting an AI agent trigger a real, irreversible business action (e.g., releasing a payment) while keeping the decision auditable and bounded.

The pattern separates three distinct layers instead of letting one LLM do everything end-to-end. First, a generative model (e.g., Claude) handles evidence gathering, tool orchestration, and natural-language explanation — open-ended reasoning tasks where flexibility is an asset.
