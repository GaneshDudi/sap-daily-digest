Debugging per-item field control in Manage Purchase Orders (F0842A)

The case: a field-control implementation, MM_PUR_S4_PO_FLDCNTRL_SIMPLE, loops over fieldselection_table and sets <fs>-fieldstatus to '+' or '-' depending on a custom product indicator read from I_Product via purchaseorderitem-material. The author reports the right status per item, but the UI shows the previous item's visibility.

First, check the logic. The code uses to_upper( <fs>-field ) CS '...'. CS is a contains-string test, so any field name containing the literal matches. With custom fields that share a prefix, such as ones numbered 1 to 7, a short name can match several entries. Replace it with EQ against the exact field name and re-test. The field list in the post is truncated ('+ 3 more fields'), so check the full list for overlaps.

Second, separate server from UI. Log or debug the BAdI call for two items with different products. If both calls return the correct status, the problem is in what the object page applies. The fact that Adapt UI plus refresh fixes it fits that reading, but the post does not prove it. Also confirm the product indicator is read per item and not once and kept in a variable.

The companion logic has three parts: MM_PUR_S4_PO_MODIFY_ITEM clears fields on modify, and BD_MMPUR_FINAL_CHECK_PO checks on save. Make sure all three use the same condition, otherwise a field can be hidden yet still mandatory.

  • fieldselection_table and fieldstatus
  • CS vs EQ comparison
  • I_Product read per item
  • server logic vs UI state
  • modify and final-check consistency

Senior A BAdI that sets field status per PO item returns correct values, yet the Fiori object page shows the previous item's visibility. How do you investigate?

First verify the server side. Log the field status returned for two items with different products and confirm the product indicator is read per item and not cached in a variable. Then review the matching logic. A substring test such as CS can match more fields than intended, so use equality on the exact field name. Check that the modify logic and the final save check use the same condition, otherwise a field can be hidden yet mandatory. If the server output is correct for every call, the cause is on the UI side. In the reported case Adapt UI plus refresh fixes it, which suggests UI state, but that is not confirmed. At that point you would raise it with SAP with a reproducible two-item scenario.

Mid-level What is the difference between CS and EQ in ABAP, and why does it matter in field-control code?

EQ compares the whole value. CS is true if the left operand contains the right one as a substring, and it is not case-sensitive. In a loop over a field table, a test like to_upper( field ) CS 'NAME' matches every field whose name contains that text. Custom fields often share prefixes or fragments, so one condition can set the status of several fields. The fix is to compare the full name with EQ, or to use a constant per field. You should also test with all fields in the list, not only one.

Architect How would you decide whether a classic API can be used in an ABAP Cloud development?

Check its release state. In ADT the object properties show the API state for the current release. For a broader comparison, SAP publishes per-release API state files that list the state of each object, and you can compare two releases to see what changed. Use released APIs where they exist. If none exists, look for a released successor or an approved extensibility option rather than calling the classic object. Record the release you checked, since the state can change between releases.
