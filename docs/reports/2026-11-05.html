Deep dives

The most valuable technical posts, explained.

RAP side effects: refreshing the header after an item action

When a RAP action on a child entity changes the parent, Fiori Elements does not know the parent changed and keeps showing old data. The post (ref 104) describes declaring side effects in the behavior definition so the UI reloads the affected entity. The excerpt does not show the exact syntax, so check the RAP documentation for the side effects section of the BDEF before teaching it.

The scenario is an item action that totals the selected items' amounts and writes the result to the header. The action implementation uses MODIFY ENTITIES on the header with the computed value, and the side effect tells the UI which entity or fields to re-read after the action.

A good lab is to build it twice. First without side effects, to show the stale header. Then add the declaration and compare the Fiori behaviour. Also test the action with several selected items and with items that are already totalled, since the sum logic is where bugs usually sit.

  • Behavior definition (BDEF) action on a child entity
  • Side effects declaration
  • Fiori Elements refresh behaviour
  • MODIFY ENTITIES on the parent
Blog: Implementing RAP Actions with Side Effects: Updating Sales O

CL_ABAP_ZIP: type mismatch and timestamp round trip

Two posts show problems with CL_ABAP_ZIP. In ref 51, zip->add( name = 'a' content = '00FFEB' ) raises CX_SY_DYN_CALL_ILLEGAL_TYPE inside ADD when it calls CRC32. The literal is a character literal, not hexadecimal. A likely fix is a hex literal such as X'00FFEB' or an xstring, but confirm it against the ADD signature in ADT.

In ref 50, an entry added with file_timestamp = VALUE #( time = '235958' ) and read back after save( ) and load( ) returns 225900 from files[ 1 ]-time on ABAP 7.58 SP 1. The author's test uses an exact xstring '00FFEB'. The post gives no cause and no answer.

ZIP stores time in DOS format, which has 2-second granularity and packed bits. That may be relevant, but the posts do not say so. Write a minimal ABAP Unit round trip, decode the DOS time by hand, and check SAP Notes for a fix.

  • CL_ABAP_ZIP add, save, load, files
  • Character vs xstring literal
  • DOS time packing
  • ABAP Unit round-trip test

XCO in ABAP Cloud: key indicator of a custom table

The author (ref 92) needs to know at runtime whether a field of a custom table is a key field. RTTI and RTTS are forbidden in ABAP Cloud, so they use xco_cp_abap_dictionary=>database_table( ... )->field( ... )->content( ). This raises CX_XCO_NEWS_EXCEPTION 'Database table ZMY_DBT does not exist'.

Their debugging suggests XCO requires the table to be C1-released, and they say tables cannot be released with C1. This is the author's claim, not confirmed.

To check: reproduce the exception, look at the table's release state in ADT, and read the documented preconditions of the XCO class. Also consider whether a released API gives the key information. Do not call it a bug without that evidence.

  • xco_cp_abap_dictionary
  • CX_XCO_NEWS_EXCEPTION
  • C1 release contract
  • RTTI/RTTS restriction in ABAP Cloud

Interview questions

Grounded in today's material. Open each one to see a model answer.

Mid-level An item-level RAP action updates the parent header, but the Fiori Elements app still shows the old header values. What is wrong and how do you fix it?

The UI only reloads what the framework knows was affected by the action. The action changed another entity, the header, so the client has no reason to re-read it. The fix described in the post is to declare side effects in the behavior definition so Fiori Elements reloads the header after the action. In the implementation, the action should read the selected items, compute the total and use MODIFY ENTITIES on the header. I would test it with several selected items and check that the header refreshes without a manual reload. I would confirm the exact side-effects syntax in the RAP documentation, since the excerpt does not show it.

Blog: Implementing RAP Actions with Side Effects: Updating Sales O
Senior In ABAP Cloud you need to know at runtime whether a field of a custom table is a key field. RTTI is not allowed and the XCO call raises CX_XCO_NEWS_EXCEPTION. How do you analyse it?

First reproduce the call with xco_cp_abap_dictionary=>database_table( ... )->field( ... )->content( ) and note the exact exception. The author suspects XCO requires a C1 release on the table, which is unverified. I would check the table's release state in ADT and read the documented preconditions of the XCO class. I would test with a table that is known to be released to see whether the behaviour differs. If the cause is the release contract, I would look for a released API or released CDS view that exposes the key information, instead of working around it. I would not call it a bug until the evidence supports that.

Architect A BAdI implementation works when you save a single business partner but is not called during a mass update. How do you find the right enhancement point?

A working single-object path does not prove the batch path uses the same code. I would also check whether the BAdI is called once per BP or once per run. Then I would choose the enhancement that sits in the flow the mass run uses. The post gives no confirmed answer, so this is the method rather than the fix.
