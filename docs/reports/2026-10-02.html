Refactoring complex SQL into CTEs without join multiplication

The post (ref 5) describes a method for restructuring long queries: identify logical stages, give each its own CTE in a WITH clause, and validate the result against the original. The main pitfall it names is join multiplication, where joining a header to a one-to-many child before aggregating inflates the totals.

The usual safeguard is to aggregate or reduce each stage to the grain of the final join key inside its own CTE, and only then join. Validation means comparing row counts and control totals of the old and new query. The source gives the method but no ABAP code, so the following is my own extrapolation, not from the post.

For ABAP work, the same staging idea applies to CDS views (one view per stage) and to AMDP or open SQL. Whether a given ABAP release supports WITH in Open SQL should be checked in your system. The post frames its use around HANA reporting and analytical queries.

Mid-level You must prevent billing document creation when a custom header field is empty. How do you approach it in S/4HANA?

First I add the field through the extensibility framework in the business context 'Sales: Billing Document'. Marking it mandatory on the UI is not enough, because other entry points such as APIs and background jobs bypass the screen. I then look for a released BAdI or custom logic extension point in the billing posting flow where I can raise an error message. In ADT I check the API state of candidates so I only use released ones. I would test both the UI path and the API path. The source question (ref 25) has no answer, so the specific BAdI must be verified in the system.

Senior Goods receipt posting date can be earlier than goods issue date through both MIGO and the API. How do you analyse where validation belongs?

Since both MIGO and API_MATERIAL_DOCUMENT_SRV show the behaviour (ref 32), the rule is either not implemented in the shared business logic or is not a standard rule at all. I would first check whether SAP standard actually enforces the rule, rather than assume it. If it is a business requirement, I implement it in the shared posting logic through a supported extension point so every entry point gets it. Putting it in a UI-only check would leave the API open. I would add tests that call both paths and compare results.

Architect How would you propose to refactor a long analytical SQL query into CTEs safely?

I split the query into logical stages, each as a named CTE. I make each stage return a defined grain, aggregating child data before joining to avoid join multiplication (ref 5). Then I validate by comparing row counts and control totals against the original query across representative data. I keep each stage readable and testable on its own. For ABAP, I check which constructs my release supports and consider CDS view stacking or AMDP as alternatives.
