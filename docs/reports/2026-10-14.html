Handling very large selection lists in ABAP SELECT

A range or select-option table with about 55,800 rows is expanded into the statement sent to the database, so the statement grows with the list. The post does not name the dump, so check ST22 first. There is no setting that safely raises the limit, and the fix is to restructure the code.

Three standard patterns apply. First, process the range in blocks of a few thousand rows in a loop and append the results. Second, use FOR ALL ENTRIES IN itab, but guard against an empty itab, which selects everything, and delete duplicates first. Third, replace the list with a join or subquery against the table that produced the belnr values, so the database does the filtering and the list is never built in ABAP.

On S/4HANA, the join or subquery in Open SQL is usually best because it avoids transferring the list at all. Compare the options on runtime and correctness, not just on whether the dump goes away.

  • IN range expansion
  • FOR ALL ENTRIES empty-table pitfall
  • Chunked SELECT
  • Join or subquery instead of a list
  • ST22 analysis

Setting partner data in VA01: exit timing

The poster fills XVBPA in USEREXIT_PRICING_PREPARE_TKOMK for partner function SP. The partner appears in the exit, but the missing-partner message returns and clears only after the Partner tab is opened. That suggests the partner screen re-reads or re-processes partner data, while the incompleteness check ran against data that did not include the change.

The lesson is that where you write data matters as much as what you write. Pricing exits run for pricing preparation, which is not the same point as partner determination or the completeness check. Use the debugger with breakpoints in the incompleteness check and the partner processing to see the order, then choose an exit or BAdI that runs before the check.

The code also contains hardcoded test values (land1 'US', name1 'TEST 1234 ') and a chained assignment assigned_bp = lifnr = .... Remove the test values and split the assignment so each field is set explicitly.

Idempotent BAdI side effects: RSROA_VARIABLES_EXIT

The BW exit RSROA_VARIABLES_EXIT is called when the variable screen opens and again on confirmation. At open time, I_T_VAR_RANGE still holds the previous value, so a logger that writes on every call records the old value and then the new one.

The post does not say whether this is documented behaviour, so treat it as observed behaviour to verify. A robust logger should not assume one call per user action. Compare the incoming ranges with the last logged entry for the same user, query and variable, and write only on a change. The exit's call phase may also be available as an import parameter, which should be checked in the BAdI definition.

Test by reproducing the sequence: open the screen, change the value, confirm, and count the rows written.

  • RSROA_VARIABLES_EXIT
  • I_T_VAR_RANGE
  • Deduplication
  • Side effects in exits

Mid-level A SELECT with an IN-range of about 55,000 entries dumps. How do you fix it?

First read ST22 to find the actual error, because the cause may be statement size or memory. Raising a limit is not a robust fix. I would process the range in chunks of a few thousand rows in a loop. Alternatively, use FOR ALL ENTRIES, guarding against an empty driver table because that selects all rows, and deleting duplicates first. The best option is often a join or subquery against the table that produced the values, so the list is never built in ABAP. I would compare the options on runtime and on result correctness.

Question: ECC Number more 50000 in Range for select.
Senior A custom BAdI that writes a log entry runs twice per user action. How do you design for it?

Do not assume one call per action. In the BW exit RSROA_VARIABLES_EXIT, the reported behaviour is a call on opening the variable screen, with the old value, and another on confirmation. I would check the BAdI definition for a parameter that identifies the call phase. Where there is none, I would compare the incoming values with the last logged entry for the same user, query and variable, and write only on a change. This makes the exit idempotent. I would test by reproducing open, change, confirm and counting rows.

Question: RSROA_VARIABLES_EXIT BAdI logs previous Input Variable value
Senior Data you set in a VA01 user exit appears in the exit but the document still reports it missing. How do you diagnose it?

I would check where the exit runs relative to partner determination and the incompleteness check. The pricing-prepare exit runs for pricing, which may be later or earlier than the check that reads VBPA. I would set breakpoints in the incompleteness check and partner processing, and watch whether the XVBPA change survives to the saved document, including the update flag. Then I would move the logic to an exit or BAdI that runs before the check. I would also remove hardcoded test values and avoid chained assignments that hide errors.
