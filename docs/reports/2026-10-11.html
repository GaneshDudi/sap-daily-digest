Reverse lookup of BRF+ callers: why the GUID search fails and what to try

RS_ABAP_SOURCE_SCAN does a text search over ABAP source. It finds the GUID only if the caller contains it as a literal. Callers of BRF+ functions usually do not. The post indicates the caller is a Z* program invoking a function in a Z* application, and the GUID is not in its source. A search on the GUID therefore returns nothing, which is expected, not a tool fault.

CL_FDT_FUNCTION=>PROCESS( ) is the runtime entry point that executes a BRF+ function. Setting a breakpoint there during a test run would show the call stack at runtime, but that is a runtime observation, not a static where-used. The post says it did not reveal the caller, and I would not expect a static answer from it.

Suggested approaches, based on the post's context and not confirmed by the thread: (1) search the source for the technical names instead of the GUID: the BRF+ application name, function name, or the Z* function module name, using RS_ABAP_SOURCE_SCAN or Code Search in ADT; (2) run where-used on the Z* function module that wraps the BRF+ call; (3) search for the application ID or related object names such as decision tables; (4) check the BRF+ application's own usage or consumer configuration.

If the caller resolves the function by name at runtime, for example from a customizing table or a constant defined elsewhere, no single static search will find it. In that case combine a search on the lookup source with a runtime trace or a breakpoint on PROCESS( ) in a test scenario.

  • RS_ABAP_SOURCE_SCAN searches literals only
  • CL_FDT_FUNCTION=>PROCESS( ) is execution, not reverse lookup
  • Search by technical name or wrapper function module
  • Runtime breakpoint or trace as fallback

Senior A Z* BRF+ function is identified only by its GUID. A source scan for the GUID finds no caller. How would you find the consuming ABAP program?

First, I would recognise that RS_ABAP_SOURCE_SCAN only matches literals, so a miss means the caller does not hard-code the GUID. I would then search for the technical names of the BRF+ application and function, and for the Z* function module that likely wraps the call, using the source scan or Code Search in ADT. I would run where-used on that function module. I would also search for related names such as decision tables and check any usage information on the BRF+ application. If the name is resolved at runtime, for example from customizing, I would find the lookup source. As a fallback I would set a breakpoint in CL_FDT_FUNCTION=>PROCESS( ) and run a test scenario to read the call stack. These are practical approaches; the static search is never guaranteed to be complete.
