Calling classic function modules from RAP: released APIs and CALL DYNPRO

The post (37) describes calling MILL_OC_ORDER_MERGE from a RAP behaviour class on S/4HANA 2023. The syntax check complains because the function uses CALL DYNPRO. The post gives no answer, so the following is general reasoning, not a confirmed fix.

In ABAP Cloud-style development, code may only use released APIs. In ADT, open the function module and check its API state in the properties (the API State tab). Dialog-oriented modules are normally not released. If the strict language version applies to the behaviour class, the check will reject them. In a standard-ABAP behaviour class, the restriction may come from the RAP context, where dialog processing is not permitted at all.

Options to evaluate: look for a released BAPI or a released business object for production orders or planned order conversion; ask SAP via an influence request or search for released CDS/RAP APIs; or wrap the classic logic in a separate unreleased class used only in a tier where classic ABAP is allowed, called through a clearly isolated interface. A dialog function that relies on screens may not work outside a dialog session even if the call compiled, so test it with batch input style alternatives only as a last resort.

Teach students to check the API state first, then search released objects, before writing a wrapper.

  • CALL DYNPRO in RAP context
  • Released BAPIs and business objects

AUTHORITY-CHECK with empty values

Post 85 asks why a custom authorization object field with a blank value still gives SY-SUBRC 4. Role data, the call and SU53 are missing, so the cause is unconfirmed. This is a checklist.

First, see what the role really holds. In PFCG, a field with no value maintained is not the same as a field holding a literal blank. The ' ' typed in a source field of the object is not a role value. Check the role's authorization data for the object and confirm the field has an entry.

Second, see what is passed. AUTHORITY-CHECK OBJECT 'ZOBJ' ID 'ZFIELD' FIELD lv_value compares the value of lv_value against the role. An initial character variable and the literal ' ' are both a blank in ABAP, but the role must contain a matching entry. If the field should be skipped, the check can use ID 'ZFIELD' DUMMY, which disables the check for that field.

Third, run the check, then open SU53. It shows which object, fields and values were checked and what the user holds. Compare them.

  • SU21 authorization objects
  • PFCG role data
  • ID ... DUMMY
  • SU53 analysis

Hidden annotations after a UI upgrade in a custom RAP report

In post 71, custom fields in a RAP report disappeared from the field catalog after a UI upgrade. All were flagged hidden and removing the hidden annotation restored them. No cause is confirmed.

The likely place to look is @UI.hidden in the CDS view entity or a metadata extension. Fields added through custom field extensibility may get annotations generated by the tool, so check the generated extension too. Also check whether the annotation is static (true) or driven by a path to another field, since the evaluation could differ between versions.

A practical method: read the effective annotations for the entity in ADT, compare with a system before the upgrade, then check the UI5 release notes and SAP Notes for the stated version. The version string in the post may not be exactly SAPUI5 1.120.x, so confirm it first.

Grounded in today's material. Open each one to see a model answer.

Senior A RAP behaviour class must reuse a classic function module that uses CALL DYNPRO. How do you approach it?

First, check the module's API release state in ADT, since unreleased and dialog-based modules are not allowed under ABAP Cloud-style rules. Then search for a released BAPI, CDS view or RAP business object that does the same job. If none exists, consider an isolated wrapper in a context where classic ABAP is allowed, with a clear interface. A function that depends on screens may not run correctly outside a dialog session, so it must be tested. I would also consider requesting a released API from SAP. Avoid hiding the dependency, because it will break on upgrade or in a cloud move.

Discussion: Function Module MILL_OC_ORDER_MERGE for order combination
Mid-level AUTHORITY-CHECK returns SY-SUBRC 4 for a custom object field that should allow an empty value. What do you check?

Start with PFCG and confirm the role holds an entry for that field. Not maintained is different from a blank. Next confirm what the program passes in FIELD, and compare with SU53, which shows the checked values. If the field should not be checked in a given call, use ID 'FIELD' DUMMY. Also confirm the user's authorizations were refreshed after the role change. Finally verify that the object definition in SU21 matches the call's field names.

Senior After a UI upgrade, custom fields disappear from a RAP-based report and are flagged hidden. How do you investigate?

I would first confirm the exact UI5 and backend versions. Then read the effective annotations of the entity in ADT, including metadata extensions and annotations generated for custom fields. I look for @UI.hidden, whether static or path-based. I compare with a system before the upgrade and read the release notes and SAP Notes. Removing the annotation is a workaround, not a diagnosis. A regression test of the field list after each upgrade would catch it earlier.
