Deep dives

The most valuable technical posts, explained.

SQL 305 in CDS: to-one associations and data-dependent failures

SQL 305 means a query expected to return one row, such as a to-one association or scalar subquery, returned more than one at runtime [87]. The thread describes a view with left outer joins to two CDS views plus associations in both a base and a consumption view. It fails in production but not in dev.

The principle is that a [0..1] or [1] cardinality is a declaration, not a check. If the join condition does not cover a unique key of the target, duplicate data can break it. Dev and sandbox data rarely have those duplicates, so the defect appears only in production.

ST05 did not show the failing statement in this case. A general approach, not a confirmed fix from the thread, is to take the production keys and run the join condition as a plain SELECT, for example SELECT key FROM target GROUP BY key HAVING COUNT(*) > 1, then compare it against the declared cardinality. Check the base and consumption views separately.

Fixes include joining on the full unique key, restricting the target with filter conditions in the association, or aggregating or picking one row explicitly. Declaring the correct cardinality ([0..*]) is honest, but then the consuming view must handle several rows.

  • SQL 305
  • Association cardinality [0..1]
  • Left outer join fan-out
  • Unique join keys
  • GROUP BY / HAVING COUNT(*) check

Enqueue lifetime in BAPI_SALESORDER_CHANGE (V1 042)

The post says the second concurrent call fails immediately with V1 042 [82]. Its claims, from reading S/4HANA 2020 and 2023 code, are that the lock is taken at read time, covers the whole sales document, does not wait, and is held until the update ends. The lock object and enqueue module are not named in the supplied text.

The key point is that a lock held until the update task finishes outlives the BAPI call. A caller that does not commit, or whose update is slow, keeps blocking others. A caller that expects a retry-wait will not get one, because the enqueue does not wait.

To check this yourself, run the BAPI in two sessions, watch SM12 while the first call is uncommitted, and compare lock release after BAPI_TRANSACTION_COMMIT with and without wait. Then design the caller to catch V1 042 and retry with a bounded back-off.

Treat the post's claims as hypotheses until you have reproduced them on your release.

  • Enqueue/dequeue
  • Update task (V1)
  • BAPI_TRANSACTION_COMMIT
  • SM12
  • Retry with back-off

Server-side paging and delta design for large OData reads

The Datasphere post fixes TSV_TNEW_PAGE_ALLOC_FAILED by replacing one unbounded GET on A_SlsPrcgConditionRecord with paged calls: a $count, then $top/$skip pages of an example size of 50000 [5]. The target uses UPSERT by primary key, so reruns are idempotent.

The delta filters on NumberOfDaysSinceLastChange eq 1, unions this with creation-date records, and sets Depth 2 so the validity entity is expanded in the same call. These are described as virtual filter properties, so confirm they exist in your S/4 release.

The weaknesses are the ones a service owner should know. A day-granular change filter misses deleted condition records and misses a day if a run fails. $skip paging can slow down on very large tables. Applying the same ideas to your own RAP or OData services means providing stable ordering, bounded page size and a change timestamp or delete marker.

  • $top/$skip paging
  • $count
  • Delta via change filter
  • UPSERT idempotency
  • Deleted records gap

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A CDS view with left outer joins and to-one associations raises SQL 305 only in production. How do you diagnose and fix it?

SQL 305 means a construct that must return one row, such as a to-one association or scalar subquery, returned several at runtime. A cardinality declaration like [0..1] is not enforced, so duplicate target rows in production data break it while dev data does not. I would take the production keys and run the join condition as a plain SELECT with GROUP BY and HAVING COUNT(*) > 1 on the target key. I would check the base view and the consumption view separately, since both declare associations. The fix is to join on the full unique key, filter the target so one row remains, or aggregate explicitly. If several rows are legitimate, I would declare [0..*] and handle the fan-out in the consumer.

Discussion: SQL 305 Error in ABAP CDS
Senior Two parallel calls to BAPI_SALESORDER_CHANGE on one order: the second fails with V1 042. Why, and how do you design around it?

The enqueue lock on the sales document is held by the first call until its update completes, so a second call finds the document locked. According to the cited post, the lock is taken at read time, covers the whole document and does not wait. I would confirm this in SM12 with two sessions. The lock outlives the BAPI call, so the caller must commit, and a slow update extends the lock. The design response is to serialise changes per order, for example through a queue, or to catch V1 042 and retry with bounded back-off. Never loop without a limit.

Architect How would you design reliable full and delta extraction of large pricing data over OData V2 from S/4HANA?

Avoid one unbounded GET, which can cause TSV_TNEW_PAGE_ALLOC_FAILED. Use server-side paging with $count, $top and $skip and a fixed page size, with stable ordering. Load into the target with UPSERT on the primary key so reruns are idempotent. For deltas, use a change filter such as NumberOfDaysSinceLastChange plus creation-date records, and expand dependent entities in the same call. Day-granular filters miss deletes and can miss a day after a failed run, so I would keep a high-water mark and add a delete strategy or periodic reconciliation. I would also check that $skip stays efficient on very large tables.
