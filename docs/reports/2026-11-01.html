The excerpt does not show the method names, parameters or filter, so the code below is a generic pattern, not the post's implementation.

The usual steps are: find the enhancement spot and BAdI definition, check whether it is filter-dependent and whether multiple implementations are allowed, and read the method signature in ADT. In S/4HANA Cloud (the post's context), you would implement it as a customer-developer in the released extensibility model. Confirm the BAdI is released for your system type.

The design decision is which order fields go into the description: order number, order short text, equipment or functional location. The PR header description has a limited length, so concatenate and truncate deliberately. Keep the logic free of database reads where possible, since it runs in the PR creation flow.

Test by creating a PR from an order and checking the header. Also test an order with empty fields, and mass creation, so one bad order does not break PR generation.

Reading a BAdI before implementing it

Ref 3 is a good prompt for a method to inspect any BAdI. In ADT, open the enhancement spot, then the BAdI definition, and read the interface: importing, changing and returning parameters. The parameters tell you what you may modify and what is read-only.

Next, check filters and multiple-use settings. A filter-less BAdI that is not multiple-use allows one active implementation, so a conflict with an existing one is a risk. Use the where-used list on the interface to find standard call sites and see the context in which it is called.

Write the implementation defensively: guard against initial inputs, avoid commits and implicit COMMIT WORK, and do not raise exceptions the caller does not expect. Unit-test the logic by moving it into a separate class that takes plain structures, so the BAdI method only delegates.

These are general practices, not claims from the post. The actual BAdI signature must be taken from the system or the full blog.

Senior Why prefer a BAdI over an implicit enhancement or modification in a cloud system?

In S/4HANA Cloud, extensibility must use released, stable interfaces so upgrades do not break custom code. A BAdI is a published contract with a defined signature, which SAP is expected to keep compatible. Modifications and unreleased enhancements depend on internals that can change. A BAdI also supports a clean separation: the implementation sits in customer code and can be removed without touching standard objects. The tradeoff is that you can only change what the BAdI exposes, so you must check that its parameters cover the need.
