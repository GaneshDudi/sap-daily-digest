RAP actions vs factory actions vs functions

In a RAP behavior definition, an action changes data. A function only reads and returns a result, so it must not modify the instance. The tutorial declares action (features : instance) startTask result [1] $self, and a parameterised action setPriority parameter ZA_TaskPriority, where the input is an abstract entity.

A factory action creates a new instance from an existing one. The tutorial declares factory action (features : instance) copyTask [1]. Its implementation fills a create request for the new key, rather than changing the source instance. A function getDaysLeft result [1] ZA_TaskDays returns an abstract entity and does not change the database.

The BDEF is managed, strict ( 2 ), with draft and lock master total etag LastChangedAt. Instance feature control makes the buttons state-dependent. One caution: the draft table ztask_d uses mandt and taskid, while the active table uses client and task_id. A draft table normally mirrors the active table's fields, so check this before copying. The excerpt also ends mid-draft-table, so the implementation class and service binding are not shown.

Raising a RAP business event from a classic billing event

The chain starts with SWE2 linkage on the billing creation event of CL_SD_BIL_BD_EVENT. It calls a receiver function module, which calls a public static method in the behavior pool. The method runs RAISE ENTITY EVENT, because RAP events can only be raised from behavior implementation code. The behavior pool is declared ABSTRACT FINAL and the method takes TYPE TABLE FOR EVENT zi_billingdoccreated~created.

The BDEF declares event Created parameter ZD_BillingDocCreated. The abstract entity carries the payload. @Event.context : { attribute: 'xsapbilltype', position: 1 } maps fields into CloudEvents context attributes, so a broker can filter without reading the payload. The root view entity selects from the released I_BillingDocument.

To verify, switch on the event trace in SWELS, run VF01, then check SWEL for category CL, type CL_SD_BIL_BD_EVENT, event CREATED. Publishing uses an .evtbnd event binding and /IWXBE/ configuration (/IWXBE/OUTBOUND_CFG, /IWXBE/EVENT_FILTER). The post is truncated, so the handler logic and /IWXBE/ setup are incomplete.

REF TO vs by-value in OO enhancement classes

The question concerns set_data on an exit helper class, with parameters typed vbdkr, nast, edidc, vbdpr_tt and komv_t. The author argues that copy-on-write sharing means by-value passing costs nothing until data changes, so memory is no concern.

That is too strong. Changing to REF TO does not remove copying by itself, since a copy still happens when either side writes to shared data. The practical risk is semantic. The object holds a reference, so later changes by the caller become visible, and state can go stale or be shared across repeated exit calls. The exit runs several times per invoice, so this matters.

A good test: call set_data, modify the caller's table, and print the object's view under both signatures. Passing global data of SAP programs by reference also couples the object to the caller's data lifetime. Treat copy-on-write as an implementation detail to verify, not a language guarantee.

  • copy-on-write sharing
  • aliasing
  • exit called multiple times
  • data lifetime

Interview questions

Grounded in today's material. Open each one to see a model answer.

Mid-level When do you use a RAP action, a factory action and a function?

An action changes data and appears as a button, optionally with feature control per instance. A function only reads and returns a result, often an abstract entity, and must not modify the instance. A factory action creates a new instance from an existing one, as in copyTask. Parameters and results can be abstract entities. The tutorial uses features : instance to enable or disable the actions depending on instance state. The rule of thumb is: if it changes data, it is an action, otherwise a function.

Blog: SAP RAP Actions, Functions and Factory Actions Explained Sim
Senior Why does a RAP business event need a wrapper method, and how would you trigger one from a classic event?

RAISE ENTITY EVENT can only be used inside behavior implementation code, so non-RAP code cannot raise the event directly. The pattern is a public static method in an abstract final behavior pool that takes TYPE TABLE FOR EVENT <entity>~<event> and raises the event. A classic event linked in SWE2 calls a receiver function module, which calls that method. The payload is an abstract entity, and @Event.context maps selected fields to CloudEvents context attributes for broker filtering. The trace can be checked in SWELS and SWEL. Publishing needs an event binding and /IWXBE/ configuration.

Architect A teammate changes IMPORTING parameters from by-value to REF TO to save memory in an exit helper class. What do you check?

First, whether memory is a real issue, since copy-on-write may already avoid a copy until data is changed. That is an implementation detail, not a language guarantee. With REF TO the object sees later changes made by the caller, so stale or shared state can cause bugs, especially when the exit is called several times per document. A copy still happens if either side writes to the data. Passing global data of the calling program by reference couples the object to the caller's data lifetime. I would test with a small program that changes the caller's table after set_data, and choose by design clarity unless measurements show a problem.
