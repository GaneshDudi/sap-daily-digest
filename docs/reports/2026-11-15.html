Diagnosing stale metadata after activating a RAP service change

The post (ref 5) describes the symptom: activation succeeds, but the consumer behaves as if nothing changed. It names a metadata cache as the cause without saying which one. The text gives no transaction, report or API, so the specifics below are a diagnostic approach, not facts from the post.

Start by asking what changed on the server. Activating a CDS view, service definition or behavior definition changes repository objects. A service binding exposes the service, and consumers read its $metadata document. Candidate holders of old metadata are the server-side Gateway metadata cache, the browser, the Fiori launchpad, and any consumer-side proxy or generated client. The post does not say which one applies.

A workable method is to fetch $metadata directly, for example in a fresh browser session or a REST client, and compare it with what the UI sees. If the direct response is current and the UI is stale, the problem is on the client side. If the direct response is stale, look at the server. Senior After you activate a change to a CDS view and RAP BO, the Fiori app still shows old behaviour. How do you find out where the stale state is?

Separate server state from client state. First confirm the objects are active and the service binding is published. Then request $metadata for the service directly, in a fresh session or a REST client, and compare it with what the app uses. If the direct response shows the change, the staleness is on the client side, such as browser, launchpad or a consumer proxy. If it does not, the server side needs investigation, including any Gateway metadata cache. Clear one layer at a time and recheck $metadata after each step, so you know which step fixed it. Mid-level Which artefacts are involved when you expose a RAP BO as an OData service, and which of them can affect what a consumer sees in `$metadata`?

The CDS data model and projection views define the entities and fields. The behavior definition and projection define the operations and actions. The service definition selects which entities are exposed. The service binding publishes the service for a protocol such as OData V2 or V4 UI. A change to any of these can change $metadata. Activation updates the repository, but a consumer sees the change only if it reads fresh metadata. That is why you check the raw $metadata response after changes. The source post lists these same artefacts as the ones whose changes appear not to take effect.
