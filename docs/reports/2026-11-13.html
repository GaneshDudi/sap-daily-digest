Deep dives

The most valuable technical posts, explained.

File upload and download in OData V2 with GET_STREAM and UPDATE_STREAM

In a SEGW project, an entity type is marked as a Media Entity (Media checkbox). This makes the Gateway framework treat the entity's content as a binary stream, addressed via $value, and not as a normal property. The runtime then calls /IWBEP/IF_MGW_APPL_SRV_RUNTIME~GET_STREAM for reads and UPDATE_STREAM (or CREATE_STREAM) for writes. You redefine them in the generated *_DPC_EXT class. The source post (92) is shown only as an introduction, so the details below are general Gateway practice, not taken from it.

In GET_STREAM, read the key from IT_KEY_TAB, fetch the content as xstring, and fill ER_STREAM with a ty_s_media_resource (value and mime_type). The mime type matters, since the client uses it to render or download. In UPDATE_STREAM, the incoming binary arrives in IS_MEDIA_RESOURCE-VALUE, and the mime type in IS_MEDIA_RESOURCE-MIME_TYPE. Persist both, with the filename if the client sends it in the slug header.

Compared with base64 in a string property, streams avoid about 33% payload inflation and keep large files out of JSON. The trade-offs are that a media entity needs a separate call for metadata and content, and that the Fiori upload control must be configured with the right upload URL and headers (CSRF token, slug).

  • Media Entity flag in SEGW
  • GET_STREAM / UPDATE_STREAM redefinition in DPC_EXT
  • ty_s_media_resource (value, mime_type)
  • slug header and CSRF token for uploads
  • Stream vs base64 property

Custom fields through standard BAPIs: CI_COBLX and the extension structure pattern

Post 63 reports that BAPI_PR_CREATE ignored a custom coding block field until the extension structure CI_COBLX existed. CI_COBL is the coding block include (Part 1 of the series), and CI_COBLX is its counterpart used for BAPI extension handling. The excerpt does not give the field names or code, so treat the mechanism as the reported pattern.

The general rule: BAPIs have fixed interface structures. Custom fields reach the database through the EXTENSIONIN table (type BAPIPAREX), where the structure name goes in STRUCTURE and the data is packed into VALUEPART1..4. The BAPI then moves matching fields into the target using the extension structure. If the extension structure lacks the field, the value is dropped without an error.

The post also mentions an ExtensionIn container trap and overwrite flags, which are plausible pitfalls: offsets in the packed container must match the structure, and a companion X structure (like BAPI_TE_...X) typically controls which fields are overwritten. Verify this against the full post. Debug by setting a breakpoint where the BAPI processes EXTENSIONIN and checking whether the field arrives.

  • BAPI_PR_CREATE
  • EXTENSIONIN (BAPIPAREX) container
  • FMDERIVE derivation
  • Silent field loss in BAPIs

Multiple-Origin Composition: keeping productive config clean

Post 4 describes a Fiori app moved from Web IDE to Business Application Studio. In production it uses a Principal Propagation destination. For local development, a second technically authenticated destination was needed. MOC in SAP OData Provisioning composes a single service from several backend destinations when the URL carries the ;mo segment, e.g. /odata/<namespace>/<service>;v=1;mo/<EntitySet>.

The key design choice is that the rewrite lives only in ui5-local.yaml, in the fiori-tools-proxy middleware. It maps /backend/odata/sap/Z_SAMPLE_SERVICE_SRV/ to the ;mo form, while $metadata stays on the regular ODP URL. The productive manifest.json is never changed.

Three settings mattered. Error Tolerance must be on, otherwise one failing origin (here Principal Propagation, which fails locally) fails the entire composed request. Metadata Cache was enabled, Destination-Based Metadata Caching disabled, and the existing cache cleared. The limitation is that MOC makes entities origin-aware, so code that navigates or updates by plain key may need changes. Test those paths specifically.

  • Multiple-Origin Composition (;mo)
  • Error Tolerance
  • Destination-based metadata caching
  • ui5-local.yaml with fiori-tools-proxy
  • Origin-aware entity keys

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A standard BAPI such as BAPI_PR_CREATE ignores your custom field. How do you diagnose and fix it?

First confirm the field exists in the relevant extension structure; one reported case needed CI_COBLX before the BAPI kept the custom coding block field. Custom data normally travels in the EXTENSIONIN table of type BAPIPAREX, with the structure name and packed values in VALUEPART fields. Check that the packing offsets match the structure. Debug by setting a breakpoint where the BAPI reads EXTENSIONIN and see whether the value arrives and is moved. Also check any companion X structure that controls overwrite behaviour. Unknown fields are usually dropped silently, which is why the bug is hard to spot. Finally, make sure the structure change is transported and active in all systems.

Mid-level How do you implement binary file upload and download in an SEGW-based OData V2 service, and why prefer it over base64 properties?

Mark the entity type as a Media Entity in SEGW. Then redefine GET_STREAM and UPDATE_STREAM (and CREATE_STREAM if needed) in the DPC extension class. In GET_STREAM, read the key from IT_KEY_TAB, fetch the content as xstring and return it in ER_STREAM with value and mime_type. In UPDATE_STREAM, take the binary from IS_MEDIA_RESOURCE and persist it with its mime type and, typically, the slug header filename. Streams avoid the roughly one-third size increase of base64 and keep large content out of JSON payloads. The trade-off is a separate request for metadata and content, and the client must send the CSRF token and correct headers.
