Diagnosing ADT install failures on the update site

Two posts report 'no repository found' for https://tools.hana.ondemand.com/latest [64, 9]. One user gets a not-found page in a browser. An Eclipse p2 update site is read by the installer, not rendered as a web page, so that browser result alone does not show a fault.

What the posts leave out is the exact error text and the ADT-to-Eclipse compatibility. One user is on Eclipse IDE 2026-09 and fails on VPN and mobile data [64], which makes a simple proxy cause less likely. That does not prove the Eclipse build is unsupported. Check SAP's current ADT installation guide for supported Eclipse versions and the correct URL.

A practical order of checks: copy the full message from the Install New Software dialog, or the Error Log view. Confirm the Eclipse version against SAP's documentation. Try the Eclipse proxy settings under Network Connections. Then test a supported older Eclipse build. These are diagnostic steps, not confirmed fixes.

KSII OOM on the COSS compatibility view over ACDOCA

The KSII case is S/4HANA 2022 RISE PCE, where the actual activity price calculation reads the COSS compatibility view and HANA runs out of memory at month-end [43]. COSS is no longer a physical table in S/4HANA. The view derives its rows from ACDOCA, so a read may aggregate a large volume of line items at runtime.

The poster asks about the USE_HEX_PLAN hint, and whether it lowers memory without changing results [43]. The post offers no confirmation, so do not present it as a fix. Treat it as a candidate to test in a non-production system, with result comparison.

A sound approach: capture the failing statement from the HANA OOM trace or SQL plan cache. Check statement memory limits and the selection scope (period, controlling area, version). Search SAP Notes for the KSII version and the S/4HANA release. Then escalate with trace evidence. A temporary memory increase is a Basis or provider decision.

The post gives hypotheses to check, not facts. Look at the underlying data element and domain for case-sensitivity (the lowercase flag), any conversion exit, the value help annotations on the CDS view, and custom logic on the save path. If the domain lacks lowercase, ABAP-side values are uppercased by design.

To trace it, compare the field definition in the extension with the CDS value help key and text fields. Test whether the value is changed on selection (UI) or on save (backend). Ask SAP whether it is a known limitation of F3425A.

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A KSII run fails with HANA out-of-memory when reading the COSS compatibility view. How do you approach it?

First, recognise that COSS in S/4HANA is a compatibility view over ACDOCA, so reads aggregate line items at runtime and can use large memory. Capture the failing statement from the OOM trace or SQL plan cache and note the selection scope such as period, controlling area and version. Search SAP Notes for the specific release and KSII behaviour. Hints such as USE_HEX_PLAN may change the plan, but I would test them on a non-production copy and compare results before relying on them. Statement memory limits and temporary memory increases are Basis or provider decisions. Escalate with the trace evidence.

Question: KSII (actual activity price calculation) – HANA OOM on COSS
Senior A custom field with a CDS value help is uppercased in a new Fiori app but not in the old one, and save validation fails. Where do you look?

I would first compare how the field is typed. A domain without the lowercase flag, or a conversion exit, will uppercase values on the ABAP side. Then I would check the CDS value help definition and annotations, to see whether key and text fields are mapped as expected. Next I would find out whether the change happens in the UI on selection or in the backend on save, using the network trace and a debug session. I would also look for custom logic on the save path. If none explains it, it may be a limitation of the new app, so raise it with SAP with a reproduction. The post does not confirm a cause.

Mid-level How would you design failure handling and idempotency for an integration that pulls OData data into middleware and retries failures?

Separate transient errors such as connectivity or timeouts from permanent business errors such as invalid payloads. Retry only the transient ones, with limits. Send permanent errors to an exception path, and persist failed messages in a data store or queue for reprocessing. Do not trust a 200 response alone, because it can carry a business error. For idempotency, key each message on a business key or message ID and check it before processing, so a retry does not create duplicates. For paging with $top and $skip, add a stable $orderby so pages do not overlap or skip records. Server-driven paging is preferable where the service supports it.
