Clean Core Levels A-D: A Real Decision Framework for RAP vs BTP Extensions

SAP has moved Clean Core from marketing language to a formal classification system (SAP Note 3578329, Aug 2025). Level A means the extension lives entirely in ABAP Cloud or BTP with released interfaces only. Level B is classic ABAP restricted to recommended/released APIs. Level C uses internal SAP objects but under documented governance (an explicit debt with sign-off). Level D is unmanaged modification — the thing Clean Core exists to eliminate. This gives you a vocabulary to grade any custom object in a system, not just a philosophy to aspire to.

  • ABAP Cloud vs classic ABAP extensibility
  • RAP (RESTful Application Programming Model)
  • Key User Extensibility and released BAdIs

Coupling Decides Renovate vs Re-Platform — Not 'Cloud-First'

The blog's core architectural claim: the renovate-vs-re-platform choice should be driven by coupling strength, not by a blanket cloud-first mandate. Tightly coupled logic — code that depends heavily on core data models, table structures, or synchronous core transactions — should be renovated in place using ABAP Cloud, RAP, and released BAdIs, keeping it on the S/4HANA core where the coupling cost of moving it would exceed the benefit. Loosely coupled logic — event-driven, API-consuming, or UI-only extensions — is a good candidate to re-platform onto BTP using CAP, Event Mesh, or SAP Build, where it can evolve independently of core upgrades.

  • Architectural coupling as decision criterion
  • RAP for on-core, upgrade-stable extensions
  • CAP/BTP for loosely coupled, independently deployable extensions

Interview questions

Senior SAP now defines Clean Core Levels A through D. What distinguishes Level B from Level C, and why would you deliberately choose to leave something at Level C instead of pushing it to A or B?

Level B is classic ABAP restricted to SAP-recommended and released APIs — upgrade-safe because you're only calling stable, documented interfaces. Level C uses internal, unreleased SAP objects, but under explicit documented governance: someone has signed off that this is a known risk with a remediation plan. You'd deliberately leave something at Level C when there's no released API covering the required functionality yet, and re-platforming isn't justified by the coupling or business value — you accept the upgrade risk consciously rather than either hiding it (Level D) or forcing a premature, costly rewrite.

Senior A custom Z-program has tight, synchronous dependencies on core MM/FI tables and transactions. Business wants to modernize it. Do you renovate it on the S/4HANA core or re-platform it to BTP, and what's your reasoning?

Renovate on core, using ABAP Cloud, RAP, and released BAdIs/APIs. The deciding factor is coupling, not fashion: tight coupling to core data models and transactions means the extension's value depends on being close to the data and transactional context. Moving it to BTP would introduce latency, data replication complexity, and eventual-consistency problems for something that needs synchronous, transactional access. Re-platforming makes sense for loosely coupled, event-driven, or UI-only logic — not for something structurally welded to core business objects.

Mid-level You're building a client that PATCHes an S/4HANA OData/RAP service through a custom gateway and it keeps getting rejected. What are the two most likely OData-protocol causes, and how do you fix each?

First, missing or stale CSRF token: OData write requests require a token fetched via a preceding GET with an X-CSRF-Token: Fetch header, then echoed back on the POST/PATCH — without it the service rejects the call as a potential cross-site forgery. Second, missing or mismatched ETag: RAP services use ETags for optimistic concurrency control on updates, so the PATCH must include the If-Match header with the ETag value last read via GET; if it's missing or doesn't match the current entity state, the service returns a 412 Precondition Failed. Fix both by ensuring the gateway performs the GET-then-write sequence rather than firing PATCH directly, and by not caching or stripping these headers in the proxy layer.

Clean Core is now a graded system, not a slogan

SAP has formalized *Clean Core Levels A-D* (SAP Note 3578329, Aug 2025):

*Level A* — pure ABAP Cloud/BTP, released interfaces only
*Level B* — classic ABAP, but only recommended/released APIs

If you're planning a modernization roadmap, grade your custom code A-D before you decide anything else.

Writing to S/4HANA through a proxy? Watch these 5 things

If you're driving POST/PATCH calls to S/4HANA OData/RAP services through any gateway (Integration Suite, custom MCP server, whatever) — these will bite you:

1. *CSRF tokens* — must be fetched via GET before every write
2. *ETags* — required on PATCH for optimistic concurrency; skip it, get rejected
3. *SAP_Messages/SAP__Messages* structures — strip from OpenAPI specs before loading, they break parsers
4. *Time* fields — service expects `HH:MM:SS{Z}`, not `HH:MM:SS`
5. Native Fiori/UI5 clients handle all of this for you silently — a custom proxy won't

Good reminder that RAP's OData contract has real semantics baked in, even if your client library hides them.
