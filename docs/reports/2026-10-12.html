Testing predicate pushdown on CDS table functions

Ref 20 asks the right performance question: when you put a WHERE on a CDS table function, does the filter reach the base tables, or does the whole SQLScript body run first? The author says they measured four table function styles on S/4HANA 2023 with execution plans and timings. The excerpt contains no plans, numbers or conclusion, so this briefing cannot tell you the answer. Read the full post before teaching any result.

What you can do now is set up the test yourself. A CDS table function is implemented by an AMDP method written in SQLScript. At runtime it is a HANA table function, and the consuming CDS view sends a SQL statement over it. Whether the optimizer can push the consumer's predicate through the function body depends on how the body is written. That is a hypothesis to test per style, not a rule.

A practical method: build the function over a large table, run the consumer with a selective WHERE on a key field, then inspect the plan in ADT or with PlanViz/EXPLAIN PLAN. Look at the rows produced by the base table scan and where the filter operator sits. Compare timings with and without the filter. Repeat for each body style, for example a plain SELECT, one that uses intermediate table variables, and one with parameters. Record the evidence, not the expectation.

  • CDS table function
  • AMDP / SQLScript
  • Predicate pushdown
  • HANA plan analysis (PlanViz, EXPLAIN PLAN)
  • Measure before assuming

Modelling capped comments on financial documents in RAP

Ref 51 describes a RAP app where users add up to 4 comments per financial document header (BKPF) and up to 2 per line item (BSEG), stored in a custom Z table, with a List Report and Fiori front end. The excerpt states requirements only and does not show the actual question or any answer, so the design below is a suggestion, not something from the post.

A sensible shape is a root entity for the document, with one comment entity as child, rather than touching the standard tables. The comment table key would hold the document key (company code, document number, fiscal year), a line item number (set to a fixed value, e.g. 000, for header comments) and a comment sequence number. Whether BSEG should be your reference or a released CDS view over it is something to check in your release.

The count limits are business rules on the comment entity, so enforce them in a validation on save in the behavior implementation, not in the UI alone. The validation counts existing plus new rows per document and item and reports a message on the offending instance. Also consider a determination that assigns the next sequence number. Finally, a UI-side limit can be hinted, but only the validation is reliable because it also protects API and other callers.

  • RAP root and child entity
  • Validation on save
  • Determination for sequence number
  • Key design for header vs item comments
  • Do not modify standard finance tables

Finding the right hook for save-time checks in ME51N/ME21N

Ref 35 asks which exit or BAdI to use to block saving a PR or PO when the same service number appears on two service lines of one item and ESLL-EXTSRVNO is empty. The post gives no answer, and the rule itself is ambiguous: is it a duplicate check, a mandatory check, or both? Clarify this with the business first.

The ref's technical notes name ME_PROCESS_REQ_CUST for PRs and ME_PROCESS_PO_CUST for POs as commonly considered BAdIs. The post does not confirm them, so verify in your release. Service lines are a sub-structure of the item, so check whether the BAdI methods you pick can see them, or whether another hook is needed.

A reliable way to find out is to look in SE18 for BAdI definitions matching ME_PROCESS_*, run a where-used list on ESLL-EXTSRVNO, and put a breakpoint on a save in ME21N to see what is called and with what data. Test both PR and PO, as a check in only one document can be bypassed. Confirm that display mode is unaffected and that the error message stops the save.

  • ME_PROCESS_REQ_CUST / ME_PROCESS_PO_CUST (to verify)

Senior A WHERE clause is applied on a CDS table function. How would you check whether it is pushed down to the base tables, and why can't you assume it is?

A CDS table function is backed by an AMDP method in SQLScript, so HANA executes it as a table function and the consuming CDS view runs on top of it. Whether the consumer predicate reaches the base tables depends on how the body is written and on what the optimizer can do with it. I would not assume either way. I would build the function over a large table, query it with a selective filter, and open the plan in ADT or PlanViz or EXPLAIN PLAN. The things to check are the rows coming out of the base table scan and where the filter operator sits. I would also compare runtimes with and without the filter. Then I would repeat this for each body style, because the result may differ between them. Ref 20 describes exactly this kind of measurement, but its excerpt does not show the results.

Senior Users must add at most 4 comments per FI document header and 2 per line item in a RAP app, stored in a Z table. How would you design it?

I would not change BKPF or BSEG. I would create a comment table keyed by the document key (company code, document number, fiscal year), an item number (a fixed value for header comments) and a sequence number. In RAP I would model the document as root and comments as a child entity, or a standalone BO that references the document key, depending on how the standard data is exposed in the release. A determination would assign the next sequence number. The 4 and 2 limits belong in a validation on save, which counts existing and new rows per document and item and raises a message on the offending instance. UI hints alone are not enough, since other consumers could bypass them. I would also check the authorisation for the document.

Does my predicate reach the table? Reading HANA plans for CDS table functions and views

Ref 20 asks whether a WHERE on a CDS table function reaches the base tables. The excerpt gives no result, so the class has learners measure it themselves.

  1. Recap: CDS view vs CDS table function (AMDP/SQLScript) and how each is executed on HANA
  2. Predictions: which of the styles will push the filter down
  3. Build a table function with a simple SELECT body and a consuming CDS view with WHERE
  4. Variant bodies: intermediate table variables, CE-style logic, parameters
  5. Collect evidence in ADT: SQL Console / PlanViz or EXPLAIN PLAN, and runtime
  6. Compare predicted vs actual, and record the rows scanned at the base table
  7. Rules of thumb for writing filter-friendly table functions

Hands-on exercise: In ADT on an S/4HANA 2023 system, create a table function over a large table (e.g. a header table) using AMDP. Write a consumer CDS view with WHERE on a key field. Run it with and without the filter, capture the HANA plan and runtime, and decide whether the predicate was applied at the base table scan or after the function body.
