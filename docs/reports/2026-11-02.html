Extending CDS views safely: EXTEND VIEW ENTITY and C1 release contracts

In S/4HANA Cloud Private Edition, CDS view extensions are created in ADT with EXTEND VIEW ENTITY. The source describes the key question as whether the base view is released with a C1 contract. Extending a C1-released view is classed as Level A (ABAP Cloud compliant, upgrade-safe). Extending an unreleased view, or copying it into a Z-view, has no upgrade contract, so SAP can change the underlying object without regard to your extension.

With the ABAP Cloud language version, referencing an unreleased object is a build failure, not a warning. This matters for upgrades: SUM runs ABAP activation checks against customer-namespace objects in the development system, and failures block the transport chain. The author recommends running ATC over the extension estate before each Feature Pack Stack, which is a cheap way to find problems early.

The post has no code, so here is the shape to teach (a sketch, not from the post): an extend view entity I_Xyz with { ... } in a DDLX/DDL source, adding a field from a Z-table via association or join. Before writing it, open the base view in ADT and check its release state (C0/C1). The post also separates two problems that look alike: a missing extension (your Z field is not exposed) and a missing release (the standard field exists but is not released for use).

The excerpt ends before Levels B–D, so do not teach the full classification from this post alone.

Dropping parent records by deep predicate in CPI XSLT

The poster uses <xsl:mode on-no-match="shallow-copy"/>, which copies everything unless a more specific template matches. To remove a whole record, match the record itself rather than the leaf. A template such as <xsl:template match="EmpEmployment[jobInfoNav/EmpJob/customString15Nav/cust_EC_GL_GlobalEmploymentType/externalCode = '1']"/> with an empty body suppresses the node and its subtree. This is a suggested direction, not confirmed in the post.

The shallow-copy rule does not run for that node because the explicit template is chosen for it and produces nothing. Keep the predicate relative to the repeating record. The sample XML seems to wrap two EmpEmployment elements inside another EmpEmployment, so check whether that wrapper is real. If it is, a predicate on the outer element could behave unexpectedly, for example by matching if any descendant record has code 1.

Hardening options: normalize-space(externalCode) = '1' to tolerate whitespace. For very large files, streamable XSLT (xsl:mode streamable="yes") may help, but descendant predicates can break streamability rules, so test it. Nothing in the post benchmarks any approach.

  • xsl:mode on-no-match shallow-copy
  • Template with empty body
  • Descendant predicate
  • Template matching on the repeating record
  • Streamability limits

BTP Destination Jobs versus HTTP Jobs

HTTP Jobs call an action endpoint of an app bound to the scheduler (sync or async). Destination Jobs target applications outside the scheduler's CF space or Kyma namespace, via a destination defined in the SAP Destination service in the same subaccount. Hardcoded or ad hoc URLs are rejected, so connectivity and credentials stay under destination governance.

The post lists the supported authentication types: No Auth, Basic, Client Certificate, OAuth2 Client Credentials, JWT Bearer, SAML Bearer, User Token Exchange, and Principal Propagation, which needs the Connectivity service. For on-premise targets the Connectivity service is also involved.

Open points: the post's diagram does not make clear which component performs the outbound call after the Destination service returns connection details, and the excerpt omits the dashboard steps and API payloads. Confirm both in SAP documentation, along with how run logs show failures, before designing around it.

Mid-level In CPI XSLT with an identity (shallow-copy) transform, how do you remove an entire parent record when a deeply nested child has a specific value?

Set xsl:mode on-no-match="shallow-copy" so everything is copied by default. Then add a template that matches the repeating record with a predicate walking down to the value, for example EmpEmployment[jobInfoNav/EmpJob/.../externalCode = '1'], and give it an empty body. That explicit template is selected for the node and emits nothing, so the record and its subtree are dropped. The match must target the repeating record, not a wrapper or the leaf, so check the XML structure. You can harden the predicate with normalize-space(). For very large payloads, streamable mode may help, but descendant predicates can limit streamability, so test it rather than assume.

Architect You design a large-volume sync as page-per-message jobs on JMS. What reliability issues must you address?

Retries and redelivery mean a page job can run more than once, so each page must be idempotent at the target, for example via upsert on a business key or a deduplication key per page. Offset paging is unstable if source data changes during the run, which can cause missed or duplicated records. Prefer a stable cursor, a snapshot timestamp, or a key-based range. You also need explicit retry limits, dead-letter handling, and concurrency settings, none of which the source post specifies. Finally, add monitoring for page counts and completion so a partial run is detectable.
