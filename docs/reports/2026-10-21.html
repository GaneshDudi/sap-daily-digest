Debugging a CAP draftActivate hang on HANA Cloud

The report: POST .../VendorRequests(ID=...,IsActiveEntity=false)/draftActivate never returns on HANA Cloud (free tier, @sap/cds 10.1.1, @cap-js/hana 3.1.1), but works on SQLite. The log ends at the CREATE of the active entity. The model has VendorRequests with @odata.draft.enabled and a Composition of many RequestDocuments, whose content is a LargeBinary with @Core.MediaType. The author has ruled out custom handlers, M_BLOCKED_TRANSACTIONS is empty, and redeployment did not help. The root cause is not confirmed, because the final test result is an empty placeholder.

A practical approach is to bisect. Activate a draft with no document rows, then one with an empty or tiny binary, then a larger one. If only the binary case hangs, the problem is LOB handling in the INSERT path and not the draft logic. Also test a draft with documents but without the content value, to separate the composition insert from the LOB insert.

On the HANA side, look at the statement while it hangs: M_ACTIVE_STATEMENTS, M_CONNECTIONS, and the lock views (M_TRANSACTION_LOCKS, M_LOCKS). An empty M_BLOCKED_TRANSACTIONS rules out a lock wait but not an idle connection or a stalled driver. Also check whether the free-tier instance is stopped or short of memory. These are checks, not conclusions: the post does not establish which applies.

Two more questions are open: whether the composition children are inserted in the same transaction as the parent, and whether the hybrid profile (cds watch --profile hybrid with cds bind) behaves the same when deployed. Report any result with the exact versions.

  • LargeBinary / @Core.MediaType
  • M_ACTIVE_STATEMENTS
  • M_TRANSACTION_LOCKS
  • bisecting by payload

Late item category changes and the SD item processing sequence

The poster derives VBAP-PSTYV from VBAP-WERKS in a custom table, inside USEREXIT_MOVE_F8ELD_TO_VBAP. For a manual plant change this works. For ABC/ATP plant reassignment it does not: the ATP check does not re-run after PSTYV changes, and the schedule line category is still derived for the original item category.

The poster traced the cause to old schedule line values held in MVERF, which overwrite the corrected schedule line that FM RV_SCHEDULING_TYPE_DETERMINE derives later. So the root problem is ordering: availability and schedule line data are already built when the item category changes.

The post gives no solution. Directions to evaluate (not confirmed by the post): check whether the change can move earlier, to where the plant is set by ABC; use standard item category determination and its customizing instead of a userexit; or force schedule line redetermination after the change. Each should be tested in the debugger with an ABC case and a manual case, watching MVERF and the schedule line table before and after.

  • USEREXIT_MOVE_F8ELD_TO_VBAP
  • VBAP-PSTYV / VBAP-WERKS
  • ABC/ATP plant change
  • MVERF
  • RV_SCHEDULING_TYPE_DETERMINE

Designing MCP tools over OData: what the excerpts leave open

Part 1 exposes the Business Partner (A2X) API as an MCP server on SAP Integration Suite, deployed to Integration Cell and published through Developer Hub. Part 2 connects Joule Work Desktop as client. A third post exposes standard SAP tables as tools for custom agents. None of the excerpts show tool definitions, authentication or limits.

For an ABAP team, the design questions are familiar. A tool needs a clear description, typed inputs and a bounded output. Raw table access needs a restricted field list, a row cap and an authorisation check on the end user, not a technical user. A CDS view or released API is a better surface than a table because it can carry access control (DCL) and a defined projection.

Also keep in mind that clients differ in which MCP capabilities they render. One poster asks whether Joule Work Desktop displays prompts from prompts/list, which is unanswered. Test the server with an MCP inspector, independent of the client.

  • MCP tools, resources, prompts
  • Integration Suite / Integration Cell
  • least-privilege tool design
  • CDS and DCL as the exposed surface

Interview questions

Grounded in today's material. Open each one to see a model answer.

Senior A CAP draft-enabled entity activates on SQLite but hangs on HANA Cloud at the INSERT of the active entity. How do you investigate?

First, reproduce with a minimal payload and bisect: no child rows, child rows without the binary field, then small and large binaries. This separates draft logic from LOB handling, since a LargeBinary field was the suspect in the report. Then look at HANA while the request hangs: M_ACTIVE_STATEMENTS and M_CONNECTIONS for the statement, and M_TRANSACTION_LOCKS or M_LOCKS for lock waits. An empty M_BLOCKED_TRANSACTIONS rules out a simple lock wait only. Check that the instance is running and not out of memory, especially on a free tier. Confirm that the same versions of @sap/cds and @cap-js/hana are used everywhere. Only after that would I suspect the driver or the framework and raise an issue with the minimal reproduction.

Senior A userexit changes the item category (PSTYV) on a sales order item when the plant changes. It works for manual changes but not for ABC plant reassignment. Why might that happen and how would you approach it?

The likely cause is sequence. ABC/ATP runs with the original item category, so availability and schedule line data are built for it. The userexit then changes PSTYV, but ATP does not re-run. The poster found that stale values in MVERF overwrite the schedule line category later determined by RV_SCHEDULING_TYPE_DETERMINE. I would confirm this in the debugger by comparing a manual and an ABC case, watching MVERF and the schedule line data at each step. Then I would consider moving the logic earlier, using standard item category determination customizing instead of the userexit, or forcing redetermination after the change. I would not assume any of these works without testing, as the thread has no confirmed fix.

Architect You are asked to expose S/4HANA data to an LLM agent through MCP. What design rules do you apply?

Expose a bounded, described tool and not a raw table. Each tool needs a clear description, typed inputs and a limited output with a row cap. Prefer a released API or a CDS view with access control over a table, so the projection and authorisation are explicit. Execute on behalf of the end user so that authorisation objects apply, not through a broad technical user. Restrict returned fields to what the use case needs. Log the calls. Test the server independently of the client with an MCP inspector, as clients differ in which capabilities they render. The posts today do not show how their patterns handle these points, so they must be checked before reuse.
