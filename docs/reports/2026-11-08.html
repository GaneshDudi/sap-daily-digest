Transportable CSRF token fetch in SAP API Management

Write calls to many SAP backends (for example OData services in a Gateway system) need an X-CSRF-Token obtained with a prior GET carrying X-CSRF-Token: Fetch. In API Management this is usually done with a service callout policy that points to an API provider. The problem is that the provider is a per-landscape object, so each system needs its own and the configuration does not transport cleanly.

The post describes a different approach: the callout targets the API proxy itself, so it reuses the proxy's existing provider and connection. It is said to work when OAuth or an API key protects the proxy, and to transport from DEV to PRD without new provider objects. The abstract does not name the policy type, headers or exact configuration, so those details are unverified.

To check it yourself, build a proxy to an OData service in a sandbox. Add a GET path that sends X-CSRF-Token: Fetch and captures the returned token and cookies. Then use that token on the POST. Watch session cookie handling, because the backend ties the token to the session. Finally, export and import the proxy and see which objects move.

  • CSRF token fetch (`X-CSRF-Token: Fetch`)
  • API proxy vs API provider
  • Service callout policy
  • Transport across landscapes
  • Session cookie binding of the token

Senior A write call to an SAP backend through API Management fails with a CSRF error. How do you fix it, and how do you keep the fix transportable across landscapes?

The backend requires an X-CSRF-Token obtained by a prior GET with the header X-CSRF-Token: Fetch. The returned token must be sent on the write call, together with the session cookies, because the token is bound to the session. In API Management this is typically done with a callout policy before the write. The usual problem is that the callout points to a separate API provider, which exists per landscape. A community post describes making the callout target the API proxy itself, reusing its provider and connection, so no new provider is needed per system. I would verify this in a sandbox, including cookie handling and what moves on export and import.

Architect What would you check before letting an AI agent through an MCP server deploy and test iFlows on a Cloud Integration tenant?

First, which tools the server exposes and which Cloud Integration APIs they call. Second, the credentials and scopes it uses, which should be minimal and limited to a development tenant. Third, whether the generated iFlow is inspectable, versioned and goes through normal review before transport. Fourth, how success of a test message is determined, for example through message processing logs rather than the agent's own claim. Fifth, how the tenant is protected so the agent cannot reach production. The announcement does not cover these points, so the repository must be reviewed.
