ABAP SQL versus native SQL: why the same table can return different data

The blog (ref 25) claims 292 S/4HANA tables have replacement objects, so ABAP SQL access can be redirected while native SQL reads the physical table. The MARD example is 4,860,442 rows via ABAP SQL against 3,500 via native SQL in the same client. Only the abstract is available, so the mechanism below is the generic concept from the item, not the author's confirmed explanation.

In practice this affects any code that bypasses ABAP SQL: EXEC SQL, ADBC (CL_SQL_STATEMENT) and AMDP methods using SQLScript. These read the physical table. A SELECT in ABAP SQL on the same name may go through a replacement object. Results can differ in row count and content.

A test is simple: run SELECT COUNT(*) FROM mard in ABAP SQL and the same count through ADBC or an AMDP on a test system, then compare. Do this for a few tables before claiming a general rule. Check the author's full list to see which tables are not redirected, since those are the ones where custom code is safe from the difference.

For remediation, prefer ABAP SQL or released CDS views for business reads, and review any native SQL or AMDP that touches tables in the list.

CDS change data capture on tables with surrogate RAW(16) keys (VBFA)

The question (ref 33) describes VBFA in S/4HANA 2025 with physical key MANDT plus RUUID RAW(16). Business fields VBELV, POSNV, VBELN, POSNN and VBTYP_N are non-key. The developer wants a CDS view with @Analytics.dataExtraction.enabled and trigger-based CDC for ODP delta into BW/4HANA.

Three variants failed. Manual changeDataCapture.mapping with role #MAIN on business fields gave 'mapping field does not exist' and 'No #MAIN table specified'. Automatic CDC with RUUID as key compiled, but the target rejects RAW keys, and BINTOHEX is said not to work for trigger CDC. alternativeKey with automatic CDC gave the same mapping error. MATDOC works with BINTOHEX.

The working hypothesis, which the post does not confirm, is that the mapping check needs physical key fields of the mapped table, so business keys that are not table keys fail. Test with RODPS_REPL_TEST after each change.

Options to evaluate: a view exposing a stable key, timestamp-based delta, or SLT. Check SAP documentation for whether trigger-based CDC is supported on VBFA in this release before designing around it.

Joining BKPF, BSEG and ACDOCA without row multiplication

The SE16H post (ref 61) joins BKPF (header), BSEG (entry-view line items) and ACDOCA (Universal Journal). It covers where to set filters, which key fields to compare and how to spot row multiplication, then recommends a released CDS view for complex joins.

Row multiplication happens when the join condition does not reach the full key of the many side. For example, joining header to lines on company code, document number and fiscal year is fine, but adding a second line-level table without the line item field multiplies rows. BSEG and ACDOCA overlap in content, so joining both can double-count amounts.

A check: count rows in each table for the document first, then in the join. If the join count exceeds the line count, a key field is missing. The teaser does not list the exact fields, so confirm them in the full post.

For reusable logic, build the selection as a CDS view on released views rather than SE16H, and compare results with the join.

Mid-level How do you avoid row multiplication when joining BKPF, BSEG and ACDOCA?

Join on the full key of each table: company code, document number, fiscal year and the line item where line-level tables are joined. Missing the line item when joining two line-level tables multiplies rows. BSEG and ACDOCA hold overlapping data, so joining both and summing amounts double-counts. Verify by counting rows per table for a document, then the joined result. In S/4HANA, ACDOCA is the Universal Journal and the preferred source. For repeatable logic, use a released CDS view rather than an SE16H join.
