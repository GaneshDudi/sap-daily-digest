Filtering a RAP List Report by a child-item field

The case is a header List Report that must be filtered by a field on an item entity in the composition. The source recommends against copying the item field into the header. Instead, expose the navigation path through the selection-field annotation, so the OData V4 Fiori elements filter bar applies the filter over the composition. It then relies on RAP's composition support and the OData V4 service.

The annotation entry is a path such as _Item/Field in UI.SelectionFields. In a CDS metadata extension the shape is roughly @UI.selectionField: [{position: 10}] on elements. For path-based fields, the source describes adding the navigation path to UI.SelectionFields. I cannot confirm the exact syntax from the excerpt, so verify it in your own system.

A local UI.SelectionFields annotation, for example in the app's annotation file, replaces the backend one. So if you add one path locally, you must repeat all existing selection fields, or they vanish from the filter bar. If the FilterBar fails with "reading 'map'", the author attributes it to a problem in the annotation XML, so inspect it first.

The design point is that the BO stays normalised. Denormalising item fields into the header duplicates data and needs synchronisation logic in the behaviour implementation.

  • Composition path _Item/Field
  • Local vs backend annotation override
  • OData V4 Fiori elements FilterBar
  • Avoiding denormalisation

Looping repeated items in the CIG mapping tool

The poster maps cXML InvoiceDetailServiceItem descriptions to JOBDESC in the E1ARBCIG_NONPOSERV_DETAILS segment of ARBCIG_INVOIC. With one service line it works. With two or more, every target gets the first description.

The cause shown in the post is the condition C2, POSITION EQUALS 1, combined with C1 (invoiceLineNumber not empty). It generates an XPath with InvoiceDetailServiceItem[1], so the first item is always selected. Removing C2 makes the Description XPath return a sequence of both descriptions. That sequence is then passed to fn:string-length, which accepts only a single item, hence the error.

This indicates the source is not scoped to the current occurrence. The poster asks whether Target Position or Target Value Variable looping, keyed on invoiceLineNumber or lineNumber, is the right approach. No answer is given, so treat it as an open diagnostic. The general principle is that a repeating target segment needs a loop context from the source, not a fixed index.

  • Source and target context in mapping
  • POSITION condition and generated XPath
  • Sequence vs single item in XPath functions
  • Target Position vs Target Value Variable looping

Senior A RAP List Report on a header needs a filter on an item field. How would you do it, and what pitfalls exist?

Keep the model normalised and do not copy the item field into the header. Expose the composition navigation path, such as _Item/Field, in the UI.SelectionFields annotation so the OData V4 Fiori elements filter bar can filter through the composition. Test it in the browser first. The main pitfall is that a local UI.SelectionFields annotation replaces the backend one, so the complete list of selection fields must be repeated, or the existing ones disappear. If the FilterBar fails with a "reading 'map'" error, the annotation XML is the first thing to inspect. Denormalising would duplicate data and force you to keep it consistent in the behaviour implementation.

Mid-level A UI Adaptation label change was transported but is not visible at runtime. How do you troubleshoot?

Start by confirming the adaptation was made for the exact app ID and layer that is being run. Then confirm the transport was imported into the target system and client. Clear the browser and launchpad cache and retest with the same user and role. Check whether the label comes from an annotation or DDIC text that takes precedence over the adaptation. Finally, check whether each app uses its own label for the same field, since KNVV-KVGR2 appears in two apps. The source post gives no details, so each of these is a hypothesis to test, not a confirmed cause.

Architect How would you design access for an LLM agent calling a legacy ECC system through an MCP server?

The key decision is the identity the call runs under. A shared technical user is simple but breaks authorisation checks and audit trails, because every action looks like the same user. Per-user authentication preserves the business user's authorisations, but needs a mechanism to propagate identity through the MCP server and Integration Suite to ECC. First establish the ECC release, the connectivity method and the exact endpoints to expose. Expose only narrow, governed interfaces, not raw tables. The source post only raises the question and gives no solution, so any design must be validated against current documentation.
