Deep dives

The most valuable technical posts, explained.

Binary-safe Base64 handling in ABAP HTTP uploads

The thread in ref 59 shows a typical binary-corruption pattern. The source Base64 begins with JVBERi0xLjQK, which decodes to %PDF-1.4, so the input is a valid PDF. cl_web_http_utility=>decode_x_base64 returns an xstring, which is the correct type for binary content.

The poster's second attempt used decode_base64 followed by a string-to-xstring conversion with UTF-8. This is not byte-safe: bytes that are not valid UTF-8 get altered or replaced, which corrupts PDFs and JPEGs. Text/plain survives because it is already text. This is a likely explanation for the MIME-type pattern, but the thread has no confirmed fix.

Three other points in the posted code. The upload sets Content-Type both as a header field and with set_content_type, so check what is actually sent. Use set_binary and pass the xstring unchanged to the request. The handlers call RAISE SHORTDUMP before assigning eMessage, so those assignments never run.

A practical check is to log xstrlen( lv_content ) and the first bytes, which should be 25504446 for a PDF, before the POST. Then compare them with the file in the source system.

  • decode_x_base64 returns xstring
  • UTF-8 round-trips corrupt binary
  • set_binary on the HTTP request
  • Content-Type set once
  • Verify magic bytes and length
  • RAISE SHORTDUMP ends the flow

User exits that receive batches: designing for call-count differences (RVV50R10C)

In ref 71, USEREXIT_SAVE_DOCUMENT in include MV50AFZ1 is called once per delivery in test but once for the whole run in PROD, where XLIPS holds all deliveries. The custom logic writes one Z-table row per delivery and assumes a single delivery per call.

The robust pattern is to loop over the whole table in the exit and key the Z-table write on the document number, with each call handled idempotently. That works for one delivery or for many.

The cause of the difference is not established. The poster suspects a variant parameter. Systems can also differ in configuration, support package or notes. To find it, set an external breakpoint in the exit in both systems, compare the call stack and the content of XLIPS, and compare the variant and the job's selection.

The general rule is that a user exit contract defines what data is available, not how often it is called. Do not infer the call count from observation in one system.

  • USEREXIT_SAVE_DOCUMENT
  • XLIPS
  • Loop over all items
  • Idempotent Z-table writes
  • Compare call stacks across systems

Treating ADT REST and API success signals with suspicion

Ref 2 states that the ADT REST API can return HTTP 200, 'finished' or an empty list while the action did not complete, measured on S/4HANA 2023. Only the introduction was supplied, so the eight traps are unknown here and none of them is verified.

The same principle applies to any API you call from a pipeline, including the attachment upload in ref 59, where a successful upload produced a file that would not open. A success status confirms that the request was accepted, not that the result is correct.

A defensive approach is to read back the state after every write. For example, after an activation, read the object's inactive/active status and the syntax check messages, and fail the job if they do not match what you expect. For uploads, compare length and a checksum.

Read the full post and test each trap against your own system before adding its defences to a CI job.

  • HTTP 200 is not proof of success
  • Read back state after a write
  • Empty list may mean nothing was checked
  • Verify with checksums or status
  • Test on your own release

Interview questions

Grounded in today's material. Open each one to see a model answer.

Mid-level A user exit that wrote one Z-table row per delivery works in test but misbehaves in PROD, where the exit is called once with all deliveries in XLIPS. How do you fix and investigate it?

Fix the code first: the exit must loop over all entries in the table it receives and write one row per document key, not assume one document per call. Make the write idempotent, for example with a MODIFY on the key, so repeated calls are safe. Then investigate the difference. Set external breakpoints in both systems, compare the call stack and the content of XLIPS, and compare the job variant, the selection and the support package level or notes. Do not assume a variant parameter is the cause until it is tested. The user exit contract guarantees the data available, not the call frequency, so the code should not depend on the frequency.

Discussion: Processing Issue - Program RVV50R10C
Senior Binary files uploaded through an OData service from ABAP arrive damaged, but text files work. What do you check?

Start with the type path. Base64 should be decoded with decode_x_base64 into an xstring, and that xstring must go to the HTTP request unchanged, using set_binary. Any conversion through string and a code page such as UTF-8 alters bytes that are not valid text, which fits text working and PDF or JPEG failing. Then check that Content-Type is set once and correctly, because duplicate settings may send something unexpected. Log the length and the first bytes before the POST, for example 25504446 for a PDF, and compare them with the source file. Also check the receiving service's accepted formats, as it may validate content.

Architect How would you design a CI job on the ADT REST API so that it does not trust a success response?

A 200 status or a 'finished' state shows the request was processed, not that the intended change happened. After each write, such as an activation, read back the object's state and the check messages, and compare them with the expected result. Fail the job if the read-back does not match. Treat an empty list as ambiguous, because it can mean no findings or that nothing was checked, so verify with a known failing object.
